### 遇到的问题

- **护栏第一版是"零容忍"，把三处合法历史代码判成违规**。`model_copy(update=...)` 白名单最初写成"一处都不许有"，结果 `store.py`（写路径）、`checkpoint.py`（读路径）、`dev_t031.py`（dev harness）全部命中。逐个查完才确认：前两处只把"行上更新的 5 个共享列"盖回 payload，方向是刻意设计的；第三处是 dev-only。**正确顺序是先判断存量是不是真漏洞，再决定规则边界**——否则我会为自己的新规则去改生产代码。最终改为显式白名单 + "白名单过期也失败"的双向断言。
- **`transition()` 是同一个不变量的第二条写路径**，且只有它没设闸。这类"两条路径一个不变量"是典型的 fail-open：`advance()` 拦得住，SQL 那条拦不住。
- **`model_copy(update=...)` 跳过校验是实测事实**，不是文档推测；langgraph 1.2.11 的节点更新也会把状态合并成普通 dict 而不重新校验模型（over-budget 与 extra 字段都被接受）。这两条一起决定了：图状态必须是 `TypedDict` 包一层，且每次变更都走 `advance()`。
- **我自己的操作失误**：用 PowerShell `Set-Content -NoNewline` 做文本替换，把 `graph.py` 整个压成一行。因为该文件**尚未提交**，git 恢复不了，只能整份重写（内容没丢，但白费一轮门禁）。**教训：源码改动只用编辑器工具，不要用 shell 做文本替换。**
- **环境故障**：工作区目录的文件权限缺少"取得所有权"，导致命令随机以 `SetNamedSecurityInfoW failed (Win32 5)` 失败。用 DSH 的文件权限诊断脚本修复后验证通过（1286 个对象已扫描，未改动文件内容与所有者，未移除任何授权项）。但 `.ruff_cache` / `.mypy_cache` / `.pytest_cache` 三个缓存目录仍有不继承父级的权限项且拒绝删除 → 门禁改用等价命令：`ruff check --no-cache`、`ruff format --check --no-cache`、`mypy app --cache-dir=<TEMP>`，pytest 本来就用 `-p no:cacheprovider`。

### 关键决策

- **持久化自管，不用 LangGraph 自带 checkpointer**（`compile(checkpointer=None)`）。实测确认框架的 checkpointer 确实按节点落盘，所以这是取舍不是能力限制：选它会产生第二份状态真相，而 T017 的 `RunStore` 已经有验收过的 row lock + version CAS + owner 谓词 + retention。代价是暂时没有框架原生 `interrupt()`，HITL 留 T049 决策。
- **`GraphState` = 1 个载荷通道 + 3 个控制面通道**（`decision` / `understood` / `resolution`）。后三者是"本次 invocation 的中间产物"，`resume` 时重新推导，**绝不持久化**——持久化它等于把"模型的解释"和"Java 的事实"并排放，后来的人分不清哪个是证据。
- **未识别的 intent 走 `WAITING_USER` 而不是猜**：没有目标就无从判断哪个 capability 合适。
- **evidence guard 拒绝的是那次工具调用，不是整条 run**：证据少一点仍交给 Java 判资格，它才是权威；而"没有 proposal"才拒绝。
- **`SAFE_STOP` 必须带机器可读 reason code**，由 `TerminalDecision` 的构造器保证（`SAFE_STOP` 无 reason 在类型上构造不出来）。`verification = UNKNOWN` 落 `SAFE_STOP` 而非 `COMPLETED`，因为 T017 的 retention 对 `SAFE_STOP` 保留 trace 90 天——钱可能已经动了又说不清时，trace 是唯一能对账的东西。


## 追加：T032 主链收口（终态节点 → 持久化接缝 → 失败收尸 → 生产接线）

### 今日完成（T032 后半段）

- **终态三节点**（`a7484ca`）：`finalize` 从已验证事实推导状态，`safe_stop` 复述路由拒绝的原因，`waiting_user` 结束本次 invocation 但让 run 保持可恢复。**三者都不需要任何依赖**——这正是"节点产 `TerminalDecision`、包装层统一 `transition`"（决定 A）的直接好处：决定 run 是否结束成了纯函数，不需要数据库就能测。
- **持久化接缝**（`d972b9f`）：`runtime.py` 的 `RunSession` 是 T032 里唯一写库的地方，只有两种写（同状态快照 / 生命周期迁移），每次写完替换手里的 record，所以 `expected_version` 永远是 store 刚产出的那一版。`drive_graph` 的**边界写延迟一步**：只有下一个节点开始时，"下一步去哪"才是事实，于是 `next_action` 记的是路由的**结果**，而不是对路由表的第二次抄写。
- **失败收尸**（`22fa3ae`，决定 A）：非终态出口一律先落 `FAILED` 再**原样抛出**。抛出与落盘同等重要——失败是**附加**在错误之上，不是**替代**它，所以本仓库的 bug 不会被归档成"又一个失败的 run"。两种拒绝静默：版本冲突（别人接管了）与已终态（别人结束了）——此时写 FAILED 等于过期执行者覆盖活着的。墓碑写不进去要 `logger.warning`，否则 run 留在 `RUNNING` 且没有执行者，而 `RUNNING` 刻意不可 resume。
- **生产接线**（`4a1d3a5`）：`/input` 与 `/resume` 现在真的组装图并驱动。`wiring.py` 是 10 节点 + 9 依赖的唯一组装点，**每请求组装一次**（凭据是每请求的）。

### 遇到的问题

- **`/input` 的步骤顺序是个真陷阱**：必须先"合并补充文本 + 校验长度"（此时 run 还是 `WAITING_USER`），再认领。反过来会留下一个**已认领但没人驱动**的 run——正是 A 决策要消灭的那个形状；漏掉"落盘合并后的请求"则会让图读到旧请求，补充文本只活在这次请求的内存里。
- **我又在换行上栽了三次**（今天累计）：用 edit 删尾换行会把 docstring 的结束引号和下一行代码**粘成一行**，产生语法错误。第二、三次都是这样。已给自己定硬规则：**edit 只做「整段替换成整段」，绝不用空串/尾换行做替换**。

### 关键决策

- **失败收尸归包装层（用户选 A）**：我原先写在 docstring 里的"这是调用方的策略"被推翻。理由：`RUNNING` 不可 resume，把它留给调用方等于把一条**正确性义务**外包给每个调用点（`/input`、`/resume`、将来第三个）——多一处就多一处会忘。这跟"同一个不变量有两条写路径、只给一条设闸"是同一个形状。**A 与并发冲突的相互作用已被测试钉住**：墓碑用同一个过期版本，会被同一个 CAS 再拒一次，所以冲突不会把活着的 run 覆盖成 FAILED。
- **并发冲突返回 409（用户选 B）**：查了代码，这**已经是仓库既有约定**（`runs.py` 的 `_http_error_for` 把 `RunVersionConflictError` 映射成 409 `RUN_STATE_CONFLICT`）——用户的判断对上了已验收代码。不能 500（没坏，且会污染告警口径）；不能静默重试（冲突后的安全动作取决于新状态，而这条链会动钱）。
- **补充文本明确拒绝，绝不静默截断**：截断后的请求在下游看来仍然"格式正确"，于是悄悄砍一半会变成查不出来的错误答案。超长 → 422 `USER_REQUEST_TOO_LONG`。

### 今天学到

```text
"策略归调用方"是个容易过头的原则：先问"把它留在机制层之外，谁必须记得做这件事？"
失败要【附加】在错误上，不是【替代】它 —— 否则 bug 会被归档成"又一个失败的 run"
不可 resume 的中间状态（RUNNING）= 没有执行者就永远不会被收，而且和"正在干活"长得一样
CAS 的第二次拒绝是特性：它顺手挡住了"过期执行者覆盖活着的执行者"
我的错误类型已经稳定暴露：不是逻辑，是"编辑工具的空串/尾换行操作" → 用规则治，而不是每次指望门禁
```
