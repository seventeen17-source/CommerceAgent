## 追加：定位并修复「前门路标」缺陷（同日，改在 `main`）

### 现象

多个外部 Agent 在彼此没有沟通的情况下，都独立得出「项目卡在 T015/T016/T017」的结论。起初判断为"基准错误"，但"每一次都这样"说明是系统性问题，于是回头查仓库本身。

### 根因（证据链）

- **GitHub 默认分支是 `main`**，它停在 `2026-09-19`（`af50a7b`）；
- `main` 上的 `PROJECT_PROGRESS.md` 原文写着 **「真实活跃任务是 T016」**，并把 `foundation/t016-contract-hardening` 标注为 **「👈 当前活跃分支（领先 main 119 个提交）」**，开头还特意写「务必先读这一段」；
- `main` 上的 `tasks.md` 只有 T002–T004 三个勾选，**T015–T018 全是 `[ ]`**；
- 分支列表里名字最像「当前主线」的恰好是 `feat/t016-commerce-client`、`demo/t016-flow-playground`、`foundation/t016-contract-hardening`、`foundation/t017-agent-run-trace`；而真正的主线 `dev/002-commerce-after-sales-mvp`、`feat/us1-write-verify-recovery` 排在 20 位开外，名字里看不出「当前」；
- **决定性证据**：某 Agent 报告它读到的是 `agent-service/app/ → agent/ clients/ config/`，且**没有 `trace/`**。实测各分支的 `app/` 布局：
  - `demo/t016-flow-playground`、`feat/t016-commerce-client` → `__init__.py agent/ clients/ config/`（**逐字吻合**）
  - `foundation/t016-contract-hardening` → `__init__.py agent/ config/`
  - `main` → 根本没有 `agent-service/app/`
  - `dev/002-commerce-after-sales-mvp` → 多了 `api/ llm/ security/ tools/ trace/ main.py`

结论：**它的观察是准确的**，只是读了一棵真实存在的 T016 时代分支树，而仓库的默认分支**主动告诉它「当前是 T016」**。这不是 Agent 理解失败，是仓库前门在撒谎——**过期路标比没有路标更有害**，因为它内部自洽、看起来权威，Agent 越守规矩越会掉进去。
