# 2026-10-09 — US4 T054 Resume / Verify live defect

## 今日目标与事实

在真实 `localhost:5173` / Agent / Java / PostgreSQL 环境中确认 US4 T053 审批创建与等待已通过：run `accf2136-581e-416c-93e3-157a90286f96` 创建 approval `dbe5d017-db9c-491a-ba62-bae5f6518f82`，Java 写入 PENDING；`approver-001` 通过 HTTP 将它设为 APPROVED。随后原 run 以 customer 身份调用 `/api/v1/agent/runs/{runId}/resume`，Java 成功创建 399.00 USD refund `5c674e9c-3cc7-41a1-a034-5bc5d9f594a4`，但 Agent 以 `BUDGET_EXHAUSTED` SAFE_STOP，`verification=NOT_RUN`。

## 根因

WAITING_APPROVAL 前已使用 7 步；Resume 仍从 Understand 重新解析与路由，至第 12 步才执行 refund write。Graph 在写后以累计 `step_count == max_steps == 12` 拒绝进入 Verify。业务写入成功与 Agent 权威核验成功不能混为一谈。

## 本轮 GitHub 修复（feature 分支，非本地同步）

- `graph.py`：仅对处于 RUNNING 且含已验证 APPROVED 绑定的 checkpoint，从 START 直接进入 `CHECK_ELIGIBILITY`；不重复运行模型理解/订单解析；仍须从 Java 读取最新 Eligibility。
- `routing.py`：对尚无 durable write intent 的可写请求，要求进入受保护写入前至少保留 Refund/Return Write 与 Verify 两步预算；预算不足在外部写入前 fail closed；已写入后不重复套用预留条件阻断 Verify。
- `test_t054_approval_resume.py` 与 `test_graph_routing.py`：补入口权限、真实编译图路径、预算正反边界与写后 Verify 路由测试。
