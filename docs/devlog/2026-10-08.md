  -> WAITING_APPROVAL

## 安全边界

1. Agent 请求模型里没有 status / approver / expiry / userId / synthetic token，不能表达“我已经 APPROVED”。
2. Java 返回 2xx 仍不是充分条件；Python 再核对 run/order/action/amount/riskReason，并只接受明确 `PENDING`。
3. approval create 是 state-changing Tool。transport timeout 归一为 `WRITE_TIMEOUT_UNKNOWN`，T053 不 blind retry，也不伪造 approval id。
4. `WAITING_APPROVAL` 是正常可恢复业务状态，不是 `SAFE_STOP`。只有真实 PENDING ApprovalRequest 存在时才允许进入该状态。
5. `AgentState.approval.status=PENDING` 只是创建时观察到的 snapshot；T054 resume 必须重新 GET Java ApprovalRequest，不能把旧 snapshot 当当前 authority。

# 2026-10-08 — US4 T054 authoritative approval resume / protected-write binding

## 结论

T054 已完成并经用户本机 Java/Python 全门禁验收通过。审批引用不再是“拿到一个 id 就能继续”的 capability：resume、恢复后的 fresh eligibility、以及 Java 最终 refund/return commit 三处共同证明当前动作仍然是当初批准的精确 proposal。

## Authority 链

```text
WAITING_APPROVAL checkpoint
  -> owner-authorized /resume
  -> checkpoint approvalRequestId selects the record
  -> owner-scoped GET Java ApprovalRequest
  -> require APPROVED + exact run/order/action/amount
  -> persist binding_verified orchestration fact
  -> RUNNING
  -> re-run current Java eligibility
  -> require current action/amount still match approved proposal
  -> protected refund/return Tool carries approvalRequestId
  -> Java write transaction re-reads ApprovalRequest again
  -> require owner + APPROVED + exact run/order/action/amount
  -> commit business row with approval_request_id
```

## 关键安全性质

- caller 只能重复 checkpoint 已保存的 approval reference，不能通过 resume body 提交 status/role/binding/token。
- `binding_verified` 不是业务授权，只表示 Agent 本轮曾权威重读；最终 authority 仍在 Java write boundary。
- approval id 不是 bearer token：fresh eligibility 不要求审批时，非空 approval id 会被拒绝。
- cross-run / cross-owner / cross-action / cross-amount 均不能复用一张已批准记录。
- approval reference 被纳入 durable write fingerprint，恢复时不能在同一 idempotency intent 下偷换审批记录。
