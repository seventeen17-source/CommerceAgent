## 遇到的问题

- **同一份教学协议被并行写了三遍，产生三个互不相同的 `AGENTS.md`。** `docs/map-first-teaching-protocol` 与 `docs/map-first-teaching-main` 两个分支的 `AGENTS.md` 完全相同（249 行，blob `1101540f`）；23:51 直接推送到 `main` 的那一版则是 152 行，**丢了「面试检查点」与「Java 质量门禁」两条正在被 foundation 分支使用的规则**，并且在 `## 3.` 前缺一个空行。根因是同一份长期规则文件在多条分支上各自演化，没有单一来源。
- `git fetch` / `git pull` 在本会话默认沙箱模式下直接失败：`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030E)`。这不是 GitHub 或仓库问题，是执行环境拿不到 Windows 凭据/证书存储句柄；放宽文件权限后同一条命令立即成功。
- `git switch` 被未提交改动拦住：`agent-service/app/agent/state.py` 有 3 行未提交修改，而该文件在 `main` 上不存在，切换必须删除它 → git 拒绝并 abort。教训：**切到不含某文件的目标分支前，先处理该文件的未提交改动**（提交或 stash），不要指望 git 会替你决定。

## 关键决策

- **教学协议放进仓库，而不是只靠 Skill**：Skill 可能在某个环境不可发现；写进 `docs/LEARNING_PROTOCOL.md` 后，换模型、换 IDE、换新会话都能恢复同一套教法。
- **`main` 保持「只含已合并内容」，不为了让数字好看而把未合并进度抄进 `main`**：进度文档滞后是分支工作流的正常结果。正确做法是**说明它滞后并指向活跃分支**，而不是把 `main` 的副本改写成 foundation 的状态——那只会让两个分支的同一文件继续分叉，把合并冲突变得更大。
- **补规则时采用最小追加，不覆盖 `main` 已有的改写**：`AGENTS.md` 第 2 节的措辞保留 23:51 那次重写的版本，只补它真正缺的内容，避免把一次可能的刻意精简又推翻回去。

## 今天学到

- **一份「权威规则文件」如果在多条分支上各自演化，就一定会漂移。** 表现不是报错，而是「某条分支上的 Agent 少了一条约束」，而且**没有任何测试会发现**。要么让它只有一条线，要么让差异显式可见。
- **文档滞后 ≠ 文档错误。** 判断该不该「修」之前，先问它描述的**对象**是什么：`main` 上的 `PROJECT_PROGRESS.md` 描述的是 `main` 的已合并内容，它对 `main` 是准确的；错的是**读者会把它当作全项目状态**。补一句定位说明，比改数字更有用。
- **面试压缩（可直接讲）**：
  > 分支长期并行时，进度文档的「滞后」是必然的，不是靠勤更新能消除的问题。真正要防的是**误导**：新会话读到 `main` 的进度文件，会以为 T005 还没做，然后重做一遍。做法是在导航文件里显式声明「本文件只描述已合并状态」并给出活跃分支地图。另一条经验是——`AGENTS.md` 这类权威规则文件不要在多条分支上各自演化，否则会出现某条分支上的 Agent 悄悄少一条约束，而没有任何测试能发现它。
