## 今天学到（复验部分）

- **`VerifiedCredential` 只有 `issuer` / `expires_at` / `verified_at`，没有 `user_id`/`role`**：本地验签在类型层面就拿不到身份，所以“从 JWT claim 读 role 去授权”这个错误写法在本仓库写不出来。这是比注释更硬的约束。
- **JWT 的吊销空窗**：本地验签只证明“凭据是我的且未过期”，证明不了“这个人现在还是这个角色”。管理员降权/封禁后旧 token 仍可用到 `exp`，补偿手段只有短 TTL + 每请求读权威状态。权威侧读的是 `commerce.users` 的**当前**行，`role` claim 不参与授权。
- **权威侧返回的是“当前 userId + 当前 role”**，Run 的 owner 键用的是权威 `userId` 而不是 token 里的 `sub` 原串；`status`（封禁）不在 `/me` 响应里，而是在转换器里以 401 拦掉。
- 失败语义分三档不是洁癖：认证失败 → 401；权威服务不可达 → **503**（对认证正确的客户端说“你 token 坏了”既假又不可操作）。

## 关键决策（T019）

1. **越权读与"不存在"对外不可区分（统一 404 `ORDER_NOT_FOUND`，消息逐字相同）**。检测依据是 orderId 的可枚举性：fixture 是 `order-001`，扫描成本近零，403 会把"这个 id 真实存在"泄露出去（存在性预言机）。角色/能力级拒绝使用 `ACCESS_DENIED`；`ORDER_FORBIDDEN` 已删除。
2. **停滞基准取 `max(shipments.last_event_at, MAX(logistics_events.occurred_at))`**，两个来源都空则返回 `null`，**不回落** `orders.shipped_at`。理由分两层：技术层是投影列与事件表之间无约束防漂移；语义层是"物流停滞"的基准必须是物流事实，拿订单发货时间冒充物流证据会让证据看起来比实际更充分。

## 今天学到（T019）

- **"仓储方法名带 owner"是约定，不是强制**。`OrderRepository` 有 `findByIdAndOwnerId`，但它仍然 `extends JpaRepository`，`findById(String)` 这条后门一直可用且编译通过。**授权的最终把关只能在 service 层**；数据库层若要有强制力，需要行级安全（RLS），本项目没有。
- **403 与 404 的取舍是"多一个事实"与"好调试"之间的取舍**，不是对错题。403 的字面语义包含"资源存在"；当资源 id 可枚举时，这个附带事实本身就是泄露。面试里答"我们统一 404"要能说出**为什么**（可枚举性 + 无其他泄露渠道），否则只是背了一个结论。
- **`open-in-view: false` 让"Service 返回读模型"变成硬要求而不是风格偏好**：LAZY 集合离开事务就炸，所以 `OrderSnapshot` 必须在事务内组装完。
- **失败集合的形状比失败数量更能定位问题**：既有测试一起挂 → 环境；只有新测试挂 → 代码。这个判据在 CI 里同样适用。
- **`Clock` 的价值是"让依赖时间的逻辑变成可精确断言的函数"**，与"方便"无关。同理，任何"现在几点/随机数/当前用户"都应从外部注入——这三样是让测试变得不可信的常见来源。
- **契约也会自相矛盾**：`GET /orders/{orderId}` 声明 403+404，`GET /orders/{orderId}/logistics` 声明 403+503 却没有 404。实现者不该"静默挑一个"，而应把不一致作为发现报出来——本 T 报出来之后由用户拍板统一为 404 concealment，并把它写成**契约规则**而不是某一处的实现选择，这样 T023/T025 及以后的端点自动继承。
- **concealment 的判据是"标识符能不能被猜"，不是"这个端点看起来重不重要"**。同一个后端里，可枚举的 `order-001` 需要隐藏存在性，UUIDv4 的 `run_id` 则不需要——所以"订单用 404、run 用 403"不是不一致，而是同一原则在两个输入上的不同结论。面试里被问"你们越权返回 403 还是 404"，能答出这个判据比答出某一个取值高一档。
- **"对外抹平"之后必须回答"那内部还知道真相吗"**。如果答案是否，那么"有人正在枚举别人的订单"这件事将永远无法被回溯——concealment 是在**响应层**做的，不应该把审计能力一起抹掉。
- **隐藏与"隐藏失败"是两件事**：拒绝路径上的审计、日志、遥测一旦抛异常，就会用另一种形式把刚刚隐藏的信息（"这个 id 存在"）暴露出来。凡是"只在一条分支上执行的副作用"，都要问一句"它失败时会怎样"。
- **不要因为一个静态分析器告警就去改设计**：`OrderService` 注入具体类 `AuditWriter` 触发的 `EI_EXPOSE_REP2` 是**可证明误报**（private final、只用于调用、不出公开 API），正确处置是**最窄豁免 + 写清理由**；如果为了绕过它去造一个接口，那是让工具牵着设计走，而且会把一个真实的告警类型永久掩盖掉。
