**Feature Branch**: `N/A（当前目录不是 Git 工作树，且未配置建分支钩子）`

**Created**: 2026-09-15

**Status**: Complete

**Input**: 用户希望从 0 设计一个用于 2027 校招/实习的 Agent / AI 应用开发项目；必须先研究真实招聘需求，再比较 4～6 个候选方向、反证首选方案，最后形成完整项目规格和 6～8 周实施计划，当前阶段不写代码且不预设技术栈。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用招聘证据建立能力地图 (Priority: P1)

作为准备参加 2027 校招/实习的计算机硕士生，我希望看到基于可追溯的 2026 年真实岗位样本得出的能力需求，而不是由流行技术名词拼成的清单，以便知道两个月内应该重点补齐什么。

**Why this priority**: 项目方向和后续选型都依赖这一事实基础；若招聘信号不可靠，后续设计即使完整也无法服务求职目标。

**Independent Test**: 仅交付岗位样本、来源、分类方法、能力频次与结论，即可由第三方抽查样本并复核主要结论。

**Acceptance Scenarios**:

1. **Given** 可公开访问的 2026 年岗位信息，**When** 完成市场分析，**Then** 每项高频能力结论都能追溯到具体岗位样本，并区分硬性要求、加分项和业务场景。
2. **Given** 同一技术词在不同岗位中含义不同，**When** 汇总需求，**Then** 结果按岗位族、公司类型和职责语境归类，而不是只统计关键词出现次数。
3. **Given** 某项能力仅由少量或单一来源支持，**When** 输出结论，**Then** 明确标注证据强度与不确定性，不将其表述为行业共识。

---

### User Story 2 - 比较并选择可完成的项目方向 (Priority: P1)

作为求职者，我希望在 4～6 个企业能理解的 Agent 项目方向之间进行加权比较，并获得一个有证据、有风险说明的首选方案，以便把有限的两个月投入到最有简历和面试价值的方向。

**Why this priority**: 用户明确拒绝直接锁定客服 Agent；候选比较是防止凭偏好选题和堆技术的核心决策门。

**Independent Test**: 给定能力地图和用户背景，评审者可依据固定权重重算各候选总分，并检查推荐理由是否与评分、证据和约束一致。

**Acceptance Scenarios**:

1. **Given** 至少 4 个不同企业场景的候选项目，**When** 评分，**Then** 每个候选在六个指定维度上均有 1～10 分、理由、证据强度和加权总分。
2. **Given** 用户 Java 较强、Python 工程经验较弱且只有 6～8 周，**When** 推荐首选项目，**Then** 推荐明确说明岗位覆盖、基础匹配、学习成本、最大交付风险和范围削减策略。
3. **Given** 候选得分接近或证据不足，**When** 给出推荐，**Then** 结论使用条件化措辞并指出什么新证据会改变选择。

---

### User Story 3 - 从三个角色反证首选方案 (Priority: P1)

作为求职者，我希望首选项目在最终确定前分别接受面试官、招聘经理和实际开发者视角的攻击，以便剔除伪需求、技术炫技和无法在两个月内兑现的范围。

**Why this priority**: 主动反证能防止评分模型固化早期偏见，也是用户“不顺着想法说”的明确要求。

**Independent Test**: 评审者只阅读反证记录，即可看到每个角色的主要反对理由、替代方案、被删除或降级的功能，以及最终保留或改选的依据。

**Acceptance Scenarios**:

1. **Given** 已产生第一推荐，**When** 进行反证，**Then** 三个角色各自提出项目价值、招聘辨识度、工程真实性和完成风险方面的具体挑战。
2. **Given** 某功能无法证明企业价值或面试价值，**When** 审查范围，**Then** 该功能被删除、降为可选项，或附带清晰的保留证据。
3. **Given** 反证后另一候选明显更优，**When** 更新决策，**Then** 允许更换首选，并保留变更原因和评分影响。

---

### User Story 4 - 形成技术中立的完整项目规格 (Priority: P2)

作为未来的项目开发者，我希望在选题稳定后获得一份覆盖业务定位、真实任务执行、失败恢复、安全、评估和可观测性的完整规格，以便后续技术选型和实现围绕明确价值展开。

**Why this priority**: 完整规格是规划与实现的输入，但必须建立在市场分析、候选比较和反证完成之后。

**Independent Test**: 使用附件要求的 A～Q 清单逐节审查，能够判断每项是否有具体、可测试、与业务相关的定义，且没有提前锁定实现技术。

**Acceptance Scenarios**:

1. **Given** 最终项目已选定，**When** 生成项目规格，**Then** 规格完整覆盖 A～Q，并包含 5～10 个正常与失败场景、工具风险表、评估数据结构和安全边界。
2. **Given** 某能力用普通确定性程序即可可靠完成，**When** 论证 Agent 边界，**Then** 该能力不被包装成 Agent 推理任务，并明确普通业务逻辑与 Agent 决策的分工。
3. **Given** 任一技术候选，**When** 进入选型讨论，**Then** 必须分别回答企业为何需要、项目为何需要、两个月内为何值得学习，并归入 Must Have、Should Have、Nice to Have 或“不采用”。

---

### User Story 5 - 获得每周可运行的实施与学习路线 (Priority: P2)

作为 Python 和 Agent 工程经验仍在建立中的开发者，我希望获得 6～8 周、每周都有可运行交付物的路线，并明确哪些核心部分必须亲自理解和复现，以便项目进度与面试能力同步增长。

**Why this priority**: 用户的目标不是交付一个由 AI 生成但本人无法解释的 Demo，而是在两个月内形成可验证的工程能力。

**Independent Test**: 从任意一周抽查，均能找到可演示的纵向切片或增量、验收标准、学习目标、风险缓冲和与面试知识点的映射。

**Acceptance Scenarios**:

1. **Given** 第 1～2 周的时间约束，**When** 查看计划，**Then** 已包含 User → Agent → Tool → Business System → Result 的最小纵向切片，而非连续数周只学习理论或搭建通用基础设施。
2. **Given** 核心 Agent 机制，**When** 分配开发方式，**Then** Agent 状态、工作流、工具调用、重试、检查点、检索、评估、人工审批和幂等安全被标为必须理解并可简化复现的内容。
3. **Given** 某周交付延期，**When** 使用削减策略，**Then** 优先删除 Nice to Have 和装饰性功能，不牺牲任务执行、可靠性、安全性、评估和可观测性的核心闭环。

---

### User Story 6 - 生成诚实可验证的求职材料 (Priority: P3)

作为求职者，我希望最终获得中文项目经历、简历要点、README 与 Demo 展示方案，并只引用实际测得的指标，以便将项目可信地用于投递和面试。

**Why this priority**: 求职材料是最终业务价值，但只有在项目实现与评估后才能填充真实结果。

**Independent Test**: 对照实际项目记录和评估报告，所有数字均可复现；尚未运行的结果使用占位符或目标值，绝不伪装成既成成果。

**Acceptance Scenarios**:

1. **Given** 项目尚未实现，**When** 初次生成简历模板，**Then** 未验证的指标明确标注为待测目标或占位符。
2. **Given** 后续已有可复现实验，**When** 更新求职材料，**Then** 每个量化表述都可追溯到评估版本、数据集和运行记录。

### Edge Cases

- 招聘页面失效、反爬或只能看到摘要时，不把不可复核内容当作核心证据；记录访问日期、可见字段和替代来源。
- 同一岗位被多个平台转载时进行去重，避免把复制的 JD 误判为多家公司共同需求。
- 职位标题相同但职责偏算法研究、平台基础设施或业务应用时，按实际职责重新分类。
- 2026 校招样本不足时，可补充近 12 个月实习、社招初级岗位和企业官方工程实践，但必须分层呈现，不能混为同一证据等级。
- 某候选项目总分最高但存在单点致命风险时，不机械推荐；必须执行最低门槛检查和反证。
- 需要真实企业系统但无法获得外部账号或数据时，使用业务语义真实、契约可验证的本地业务系统与合成数据，不伪称生产集成。
- 技术名词在 JD 中高频出现但对最终项目价值很低时，不因频次而强行纳入。
- 两个月进度受模型费用、外部服务限额或学习曲线影响时，规格必须提供低成本、可离线或可替代的验收路径。
- 指标提升由测试集泄漏、样本过小或人工挑选造成时，不允许写入简历结论。
- Prompt Injection、越权、高风险写操作、工具超时、错误工具、重复调用和部分失败必须有单独的失败场景及验收口径。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 交付流程 MUST 严格遵循“招聘市场分析 → 候选项目 → 第一推荐 → 三角色反证 → 最终项目规格 → 实施计划”的顺序；前一阶段未完成验收时不得把后一阶段结论当作既定事实。
- **FR-002**: 市场分析 MUST 以 2026 年可追溯的真实岗位信息为主，并记录岗位名称、公司、公司类型、地区、经验层级、发布日期或抓取日期、来源链接、职责、硬性要求和加分项。
- **FR-003**: 岗位样本 MUST 聚焦 Agent Application Engineer、LLM Application Engineer、AI Backend、AI Full Stack、智能体工程等应用工程岗位，并显式排除以预训练、RLHF、CUDA 或纯算法研究为主的岗位。
- **FR-004**: 市场分析 MUST 区分校招、实习、初级社招及仅作为趋势参考的高级岗位，不得用高级岗位要求直接替代目标岗位要求。
- **FR-005**: 能力地图 MUST 对每项能力给出出现范围、职责语境、要求级别、岗位族差异、证据强度，以及“高频但不一定值得投入”的反例说明。
- **FR-006**: 分析 MUST 独立判断用户列出的技术和概念，不得因其出现在输入中而默认必选。
- **FR-007**: 候选阶段 MUST 提供 4～6 个业务方向不同、企业痛点清晰、超越普通 ChatBot 或单纯 PDF 问答的项目方案。
- **FR-008**: 每个候选 MUST 展示 Agent 实际执行任务、真实工具调用、与企业业务数据或业务系统的连接、失败处理、评估可能性和 6～8 周边界。
- **FR-009**: 每个候选 MUST 按以下固定权重评分：企业需求匹配度 25%、Agent 技术深度 20%、面试可讲内容 20%、两个月可完成性 15%、与用户基础匹配程度 10%、差异化 10%。
- **FR-010**: 每个评分项 MUST 使用 1～10 分并附简短理由；总分 MUST 可由分项和权重重算，且不得用虚假精度掩盖证据不足。
- **FR-011**: 推荐结果 MUST 指明第一推荐、匹配的公司类型、可投岗位、胜出原因、最大风险、最小可行范围和改变推荐所需的新证据。
- **FR-012**: 反证阶段 MUST 分别从面试官、招聘经理和开发者视角回答“不值得做的原因、更好替代、伪需求、技术堆砌和交付风险”。
- **FR-013**: 反证阶段 MUST 允许重算评分、更换首选、删除功能或降低优先级，并记录每项决策的依据。
- **FR-014**: 最终项目规格 MUST 完整覆盖用户要求的 A～Q：定位、场景、架构、选型、Agent 架构、工具、RAG、业务后端、数据库、评估、可观测性、测试、部署、安全、路线、面试映射和简历输出。
- **FR-015**: 最终项目规格 MUST 包含 5～10 个核心业务场景；每个场景均说明用户输入、Agent 判断、工具、业务数据、检索、人工审批、输出和失败点。
- **FR-016**: 场景集合 MUST 覆盖工具超时与重试、错误工具选择、重复调用、Prompt Injection、越权、高风险操作、幂等和 Human-in-the-loop。
- **FR-017**: 架构说明 MUST 区分用户界面、Agent 服务、业务后端、业务数据库、检索、缓存、工具协议、可观测性和评估职责；仅在项目确有需要时保留相应层。
- **FR-018**: 每项重要技术选择 MUST 回答企业为何需要、项目为何需要、两个月内为何值得学习，并归类为 Must Have、Should Have、Nice to Have 或明确不采用。
- **FR-019**: 规格 MUST 对 Python、Java、Agent 编排方式、前端、MCP、RAG、数据存储、检索、可观测性、容器化、编排平台和 Multi-Agent 独立作出价值判断，不得继承旧项目栈。
- **FR-020**: Agent 架构 MUST 定义状态、步骤、条件流转、工具循环、校验、停止条件、最大步数、重试、检查点、记忆和人工介入；Planner、Reflection 与 Multi-Agent 仅在有明确任务需求时采用。
- **FR-021**: 工具清单中每个工具 MUST 定义名称、业务功能、输入、输出、读写属性、风险等级、自动调用权限、审批规则、超时、重试、幂等和错误处理。
- **FR-022**: 仅当存在无法用结构化业务查询合理替代的知识检索需求时才设计 RAG；若采用，MUST 定义语料、切分、语义与词法检索、融合、重排、候选数量、引用和评估边界。
- **FR-023**: 若保留独立业务后端，规格 MUST 证明其承担真实领域逻辑，并定义领域实体、数据关系、业务接口、事务、权限、幂等和审计；不得为展示语言能力而拆分空壳服务。
- **FR-024**: 数据设计 MUST 定义业务实体、Agent 运行、会话、工具执行历史和审计记录之间的关系，以及关键标识、状态、关联约束和常用查询需求。
- **FR-025**: 评估方案 MUST 定义可实际执行的 50～100 条测试样本结构，并至少覆盖任务成功率、工具选择准确率、参数准确率、策略合规率、不安全操作率、检索召回、引用准确率、平均工具调用数、端到端时延和 Token 成本。
- **FR-026**: 评估 MUST 包含 Baseline、Version 1 和 Optimized Version 的可比实验设计，并记录数据集版本、运行配置、失败分类和统计口径，避免测试集泄漏。
- **FR-027**: 可观测性 MUST 能重建单次 Agent Run 的请求、模型决策、工具与参数、工具响应、检索片段、时延、Token、错误、重试、审批和最终结果。
- **FR-028**: 测试计划 MUST 覆盖单元、业务接口、工具契约、Agent 集成、离线评估和故障注入，并为高风险写操作设置独立安全验收。
- **FR-029**: 安全设计 MUST 覆盖 Prompt Injection、工具授权、参数验证、注入攻击、敏感数据、读写工具隔离、高风险审批、审计和最小权限。
- **FR-030**: 部署方案 MUST 以两个月内简单可靠和可复现为优先，分别论证本地组合部署、云部署、持续集成和集群编排是否必要。
- **FR-031**: 6～8 周计划 MUST 每周提供可运行交付物、验收标准、需要掌握的核心知识、风险和范围削减项；最迟第 2 周形成首个端到端纵向切片。
- **FR-032**: 面试映射 MUST 对每个重要设计列出可能问题、必须掌握内容、必须能亲自复现的核心代码、可由 AI 辅助的工作和不可外包给 AI 的判断。
- **FR-033**: 求职输出 MUST 包含中文项目经历模板、简历要点、关键词、README 结构和 Demo 视频脚本；任何尚未实际测量的指标不得写成已实现成果。
- **FR-034**: 每个阶段 MUST 清楚区分事实、推断、建议、假设和待验证目标，并为外部事实提供可访问来源与访问日期。
- **FR-035**: 整体范围 MUST 优先保证 Agent 执行闭环、可靠性、安全、评估和可观测性；登录、完整 RBAC、管理后台、大量 CRUD、动画和非必要基础设施默认排除在核心版本之外。

### Key Entities

- **Job Posting Sample**: 一条可追溯岗位证据，包含来源、时间、岗位层级、职责、要求、公司与地区信息，以及去重标识。
- **Capability Signal**: 从岗位样本中归纳的能力信号，记录语境、频次、要求级别、适用岗位族、证据强度与学习投入建议。
- **Project Candidate**: 一个候选项目方向，包含企业痛点、目标用户、Agent 必要性、任务闭环、范围、风险、岗位映射和六维评分。
- **Decision Record**: 候选评分、推荐、反证意见、范围变更和最终选择的可审计记录。
- **Project Specification**: 最终选定项目的 A～Q 业务与产品规格，是后续技术计划的权威输入。
- **Agent Scenario**: 一条端到端业务任务，包含输入、判断、数据、工具、审批、输出、失败模式和验收结果。
- **Tool Contract**: Agent 可调用能力的业务契约与安全策略，包括读写风险、权限、超时、重试和幂等语义。
- **Evaluation Case**: 可版本化测试样本，包含任务、初始状态、允许动作、期望工具与参数、策略约束、期望结果和评分规则。
- **Weekly Deliverable**: 某一周可运行、可演示、可验收的项目增量及其学习和风险目标。
- **Evidence-backed Resume Claim**: 与具体评估运行和版本关联的求职表述；未验证前只能作为模板或目标。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 市场分析至少覆盖 30 条去重后的相关岗位样本，其中校招/实习与初级岗位不少于 60%，且 100% 的核心能力结论可追溯到样本或明确标注为推断。
- **SC-002**: 交付 4～6 个候选项目，所有候选的 6 个维度均有可重算评分与理由，权重合计 100%。
- **SC-003**: 第一推荐完成三角色反证，所有被识别的致命风险都有“规避、降级、验证或改选”之一的明确处理结果。
- **SC-004**: 最终项目规格对 A～Q 的覆盖率达到 100%，且独立评审可在 15 分钟内理解其业务问题、Agent 必要性、核心闭环和两个月边界。
- **SC-005**: 规格定义 5～10 个核心场景，并覆盖输入中列出的 8 类关键失败与安全情形；每个场景都有可判定的期望结果。
- **SC-006**: 技术决策表中 100% 的重要候选技术均包含企业价值、项目必要性、学习投入、优先级与不采用理由，且没有仅以“显得高级”为依据的 Must Have 项。
- **SC-007**: 评估设计包含 50～100 条可版本化样本的明确模式，10 项指定指标均有计算口径、通过阈值或解释规则，并支持三个版本的公平对比。
- **SC-008**: 6～8 周计划的每一周都有可运行验收物；第 2 周结束前可演示最小纵向切片，核心版本总工作量保持在单人两个月可完成范围内。
- **SC-009**: 面试映射覆盖所有 Must Have 模块；每个模块至少对应一个面试问题、一个必须理解的设计点和一个本人可简化复现的核心实现任务。
- **SC-010**: 求职材料中 100% 的量化成果可追溯到实际评估记录；在没有实测数据时不出现伪造的完成指标。
- **SC-011**: 一名熟悉后端但不熟悉本项目的评审者可依据规格，对任一功能判断其属于核心、延期、可选或不做，主观歧义项不超过 3 个。

## Assumptions

- 主要目标市场默认为中国大陆 2027 届校招与实习；海外岗位和高级岗位只用于对照趋势，不直接决定项目范围。
- 岗位研究以执行分析时可访问的 2026 年信息为准；访问日期与页面失效风险会被记录。
- 用户每周能够稳定投入约 15～25 小时，核心开发周期为 8 周，并允许按 6 周最小版本收缩。
- 最终项目由单人主导，AI Coding 可辅助样板、测试生成、文档与非核心界面，但关键 Agent 与安全机制必须由用户理解、审查并能复现。
- 可以使用公开、合成或脱敏数据构建业务语义真实的本地企业系统；不会声称接入了并未实际连接的生产系统。
- 当前规格定义的是“如何完成招聘研究、项目决策和最终设计”的需求边界；该阶段现已完成，后续实现由 `002-commerce-after-sales-agent` 及项目 Constitution 约束。
- 项目 Constitution 已正式建立并成为后续 Feature、Plan、Tasks 和实现的最高工程约束；001 中早期阶段性原则仅保留为选题与研究过程记录。
