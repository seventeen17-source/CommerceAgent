## 今天学到

- **「远端多了一条分支」与「多了一条能采纳的开发线」是两件事**。判断能不能采纳，先看两件事：它的**基线**（从 `main` 还是从最新 `dev` 拉的）、以及它**有没有看见已有计划**（`main` 上根本没有 `ui-productization.md`，所以它是重新规划了一遍）。

- **「聚合」在跨用户模型里不是查询问题，是授权问题**：`agent-service/app/trace/store.py` 的三条 SQL 全是 `WHERE run_id = %s`，没有列表、没有 count；「列出所有 SAFE_STOP」在当前模型下**写不出来**。

- **回放的数据会过期**：COMPLETED / ESCALATED 满 7 天清空 `state_json`，而且是**该 run 的所有 checkpoint** 一起清（`retention.py:106-112`、`store.py:767-775`）。「回放」的默认假设（payload 一直在）是错的。

## 9. 本次评估暴露的真实缺口（建议单独立项，不塞进 UI 任务）

## 本节遇到的问题

1. **沙箱不能建分支**：`git switch -c` → `cannot lock ref ... Permission denied`。提权重试成功；这条与 `PROJECT_PROGRESS.md` 里记录的环境事实一致（受限模式下 git 写操作全部失败）。
2. **「DB 有」≠「页面拿得到」**：Java 读模型是 DTO 白名单式的 —— 退款/退货 DTO 各只有 3 个字段，工单只有 `ticketId`+`status` 且**没有 GET 端点**，订单的创建时间只在列表 DTO、金额只在详情 DTO。矩阵必须按「接口给什么」写，不能按「表里有什么」写。
3. **审批视角的真实约束**：`APPROVER` 读不到订单与物流（`/orders/**` 一律 CUSTOMER），也读不到单条审批详情（`GET /approvals/{id}` 要求 CUSTOMER）—— 审批台只能显示审批行自带字段。这不是设计取舍，是当前权限事实，必须写进页面设计。
4. **字段名有语义错误**：`verifiedRefundRequestId` 读的是通用 `verification.resource_id`，退货核验成功时也会返回退货号 —— 直接照用会在 UI 上把退货写成退款。

## 本节关键决策

- **矩阵只写「接口现状 + 所需增量」，不写任务完成状态**：符合 `docs/README.md` 对设计文档的定位（设计文档不记录实现进度）。
- **幂等键/请求指纹不进投影**：重复写防护在页面上只表达「同一逻辑请求」，原文不出 Agent 服务。
- **`stopReason` 不用 `errorCode` 代替**（沿用 `ui-productization.md:48` 的既有口径）。
- **本期不新增 Run 查询标识**：响应丢失时页面显示「无法确认」，而不是新增「按身份列出 Run」的端点（后者需新契约 + 单列范围）。

## 本节学到

- **投影缺失和数据缺失是两回事**：7 个展示值里 4 个拿不到，原因全是「同一份真实数据的投影没做」，不是数据不存在 —— 这决定了 T085/T086 是加投影而不是加采集。
- **角色不是加个枚举就完事**：`SUPPORT` 在 `SecurityConfig` 里没有任何专属规则，等于今天不可用；`APPROVER` 能读全局审批队列却读不到订单。角色矩阵必须逐端点核对，而不是按名字想象。
- **契约里声明的事件类型不等于会发生的类型**：`RunEvent.eventType` 声明 9 种，生产只 emit 2 种 —— 任何「UI 等 VERIFICATION 事件」的设计都会踩空。
