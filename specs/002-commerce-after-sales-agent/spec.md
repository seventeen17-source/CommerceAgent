# 功能规格：CommerceAgent 企业电商售后执行与异常处置 Agent

**Feature Branch**: `[002-commerce-after-sales-agent]`  
**Created**: 2026-09-15  
**Status**: Draft

## 目标

构建一个面向企业电商售后的执行型 Agent。它需要能够理解含糊的用户诉求，跨订单、物流和售后政策等来源收集证据，根据当前证据动态选择下一步业务能力，在确定性业务规则约束下执行退款、退货、审批或转人工，并输出可审计结果。

本项目**不是 FAQ ChatBot，也不是固定的 intent → refund API 路由器**。

---

## 用户场景与测试

### 用户故事 1：物流异常退款闭环（P1）

消费者提出：“订单一直没收到，我不要了，帮我退款。”

系统必须定位相关订单，检查订单与物流状态，在需要时补充售后规则证据，并通过确定性资格检查判断是否允许退款；满足条件时创建退款申请并验证最终业务状态。

**为什么优先级最高**：这是最小可用业务闭环，可以同时证明自然语言理解、动态取证、Tool Calling、确定性业务规则、安全写入和最终状态验证。

**独立验收**：给定一个 `SHIPPED`、未签收、物流超过阈值无更新且金额未触发人工审批的订单，用户仅提供自然语言投诉；系统应独立完成订单定位、物流查询、资格检查、退款创建和写后验证，并且只能生成一个退款申请。

**验收场景**：

1. **Given** 用户拥有一个已发货但 120 小时无有效物流更新的订单，且后端资格服务返回可退款；**When** 用户请求退款；**Then** 系统创建且仅创建一个正确金额的退款申请，并返回可验证的退款编号与处理结果。
2. **Given** 退款创建调用发生超时且结果未知；**When** Agent 恢复流程；**Then** 系统必须先查询售后状态，并使用同一逻辑幂等标识处理，不得产生重复退款申请。

### 用户故事 2：已签收商品改走退货路径（P1）

当订单已经签收时，系统必须依据新的业务证据改变处理路径，而不是继续执行“未签收退款”。

**为什么重要**：这是 Agent Value Gate 的核心证明——中间 Tool Result 必须能够改变下一步动作。

**独立验收**：将同类退款诉求放到一个已经签收、仍在退货窗口内的订单上，系统应从退款路径切换到退货或退货退款路径。

**验收场景**：

1. **Given** 订单已签收 3 天且退货资格允许；**When** 用户说“直接给我退款”；**Then** 系统不得直接创建未签收退款，而应进入退货资格检查并创建 `ReturnRequest`。

### 用户故事 3：模糊订单澄清（P1）

当用户说“把上次买的耳机退掉”，但账号内存在多个候选订单时，系统必须先澄清目标订单。

**为什么重要**：企业 Agent 不能通过猜测关键业务对象来执行资金或状态写入。

**独立验收**：给定两个均可能匹配自然语言描述的订单，系统必须提出澄清问题，并且在用户确认前退款/退货写入计数保持为 0。

**验收场景**：

1. **Given** 当前用户存在两个相似耳机订单；**When** 用户发起模糊退货请求；**Then** 系统要求用户确认目标订单，且不得提前产生任何售后写操作。

### 用户故事 4：高风险售后人工审批（P2）

当确定性风险规则要求人工审批时，系统必须暂停自动执行并等待授权。

**为什么重要**：高风险写操作的 Human-in-the-loop，是企业 Agent 与普通自动化脚本的重要区别。

**独立验收**：给定一个满足售后资格但金额达到高风险阈值的订单，Agent 只能创建审批请求并进入等待状态；审批通过前退款/退货写操作必须为 0。

**验收场景**：

1. **Given** 资格服务返回 `approval_required=true`；**When** Agent 准备执行售后动作；**Then** 系统进入 `WAITING_APPROVAL`，只有合法审批结果到达后才允许继续。

### 用户故事 5：无法自动处理时安全转人工（P2）

当关键证据缺失、业务状态冲突、规则无法自动决策，或依赖服务持续失败时，系统必须安全停止自动写入并转人工。

**为什么重要**：企业系统首先要保证安全，而不是为了“完成任务”去猜测业务状态。

**独立验收**：关闭物流服务，或让资格服务返回 `MANUAL_REVIEW`。系统不得凭模型推断继续退款，而应创建人工工单或清晰返回需要人工介入的状态。

**验收场景**：

1. **Given** 物流状态无法在重试预算内获取；**When** 用户要求基于“疑似物流丢失”退款；**Then** 系统不得生成未经证据支持的退款，应转人工或返回证据不足状态。
2. **Given** 资格服务返回 `MANUAL_REVIEW`；**When** Agent 处理请求；**Then** 系统创建可追踪的售后工单并附带已收集证据。

### 用户故事 6：售后规则检索与可解释结果（P2）

系统可以检索非结构化售后政策，用于解释处理依据和补充上下文，但政策文本本身不能直接授权资金或业务写入。

**为什么重要**：该故事明确区分 RAG 与确定性业务规则，避免“向量库即业务数据库”。

**独立验收**：给定一个需要政策解释的售后案例，系统应返回有效政策来源/版本信息；即使检索文本声称“可直接退款”，最终资格仍必须来自确定性业务服务。

**验收场景**：

1. **Given** 检索结果包含适用售后条款；**When** 系统解释处理结果；**Then** 返回可追溯政策来源，同时最终资格与金额与确定性服务保持一致。
2. **Given** 检索到相互冲突或过期政策；**When** 无法确定有效版本；**Then** 系统不得选择任意文本作为授权依据，而应安全停止或转人工。

## 边界情况

- 用户存在多个同类订单，且自然语言无法唯一指向目标订单。
- 用户输入不存在或不属于本人的订单号。
- 订单已取消、已经存在退款/退货申请，或处于不可重复售后状态。
- 物流服务超时、返回冲突状态或长期不可用。
- 售后政策检索无结果、命中过期版本或出现冲突版本。
- 资格服务不可用、返回拒绝或 `MANUAL_REVIEW`。
- 退款/退货写操作超时且结果未知。
- 用户重复提交同一个售后请求。
- 用户通过 Prompt Injection 声称管理员权限或要求跳过规则。
- 高金额或异常商品需要人工审批。
- Agent 达到最大步骤数，或重复调用同一 Tool 且没有获得新证据。
- 写操作成功但最终状态验证失败。

## 功能需求

- **FR-001**：系统必须接受自然语言售后请求，并识别用户业务目标，但不能过早假设最终动作。
- **FR-002**：系统只能从当前已认证用户有权访问的订单中解析目标订单。
- **FR-003**：存在多个合理候选订单时必须澄清；在目标订单未确定前禁止业务写入。
- **FR-004**：系统必须在多步售后处理中维护显式任务状态。
- **FR-005**：系统必须根据当前证据选择下一项允许的业务能力，而不是对所有退款类请求执行固定路径。
- **FR-006**：不同的订单、物流和资格证据必须能够产生实质不同的结果，包括澄清、退款、退货、审批、转人工、拒绝或安全停止。
- **FR-007**：系统必须限制最大步骤数和停止条件，防止无限 Tool Loop。
- **FR-008**：Tool Result 与错误状态在作为业务证据之前必须经过验证。
- **FR-009**：退款/退货资格、最大允许金额和审批要求必须来自确定性业务规则，而不是模型输出或检索文本。
- **FR-010**：Agent 不得覆盖 eligibility、amount、ownership、approval 或合法状态迁移结果。
- **FR-011**：系统必须提供用户订单、订单详情、物流状态、售后状态和适用政策知识的读能力。
- **FR-012**：系统必须支持受保护的退款申请、退货申请、支持工单和审批申请写能力。
- **FR-013**：所有资金/状态写入都必须在服务器端依据当前业务状态完成授权与校验。
- **FR-014**：每个逻辑退款/退货写入必须幂等；用户重试、Agent 重试或网络超时都不得产生重复业务对象。
- **FR-015**：任何写请求后，系统必须验证最终业务状态，再向用户宣称成功。
- **FR-016**：权威风险规则要求审批时，系统必须暂停高风险动作。
- **FR-017**：Agent 不得自行审批、伪造审批状态或通过 prompt 绕过审批要求。
- **FR-018**：自动处理无法继续时，系统必须提供安全转人工路径，并可将已收集证据附加到工单。
- **FR-019**：非结构化政策检索可以用于政策/SOP 上下文和解释。
- **FR-020**：政策检索必须保留来源、版本和生效时间等可引用元数据。
- **FR-021**：检索文本必须被视为不可信数据，不得改变授权、Tool allowlist、审批阈值、退款金额或确定性资格规则。
- **FR-022**：用户声称“我是管理员”等 prompt 不得改变已认证 principal 或业务权限。
- **FR-023**：系统必须阻止用户读取或修改其他用户的订单和售后状态。
- **FR-024**：Agent 只能调用注册且 allowlisted 的业务能力，不得接受模型输出的任意内部 endpoint、URL、SQL 或服务名。
- **FR-025**：每次 Agent 执行必须拥有唯一 `run_id`。
- **FR-026**：每次 run 必须记录结构化状态迁移、Tool 名称、已验证参数摘要、结果/错误、重试/超时、审批状态、写入结果和最终验证结果。
- **FR-027**：失败 run 必须能够仅凭结构化 trace 重建主状态/Tool/审批/写入/验证路径，不依赖隐藏 chain-of-thought。
- **FR-028**：系统必须支持可重置的合成业务状态，用于离线 Eval，能够可复现检查预期 Tool/动作和最终状态。
- **FR-029**：系统必须维护版本化离线 Eval 数据集，不少于 60 例，目标约 74 例，覆盖正常、分支、失败、安全、审批、幂等和检索场景。
- **FR-030**：Eval 至少必须测量 Task Success、Tool Selection、Parameter Correctness、Business-State Correctness、Policy Compliance、Unsafe Action、Duplicate Write、平均 Tool 数、端到端时延和 Token 使用；涉及检索的 case 还需包含 retrieval/citation 指标。
- **FR-031**：Baseline 与 Agent 必须在可比较的数据集版本、Tool 权限、reset state 与指标定义下评估。
- **FR-032**：首个可发布版本必须聚焦售后执行，不包含广义售前推荐、商家营销、采购、通用全渠道客服和模型训练功能。

## 核心实体

- **User**：已认证用户，只能访问自己的 commerce 与 after-sales 数据。
- **Order**：权威购买记录，包含履约/售后状态和归属关系。
- **OrderItem**：用于售后规则判定的商品和品类信息。
- **Shipment / LogisticsEvent**：物流状态与事件历史，作为物流异常证据。
- **AfterSalesPolicy**：版本化的非结构化售后政策/SOP，仅用于检索与解释。
- **AfterSalesRule**：结构化、可执行、确定性的售后业务规则。
- **EligibilityDecision**：确定性资格结果，包含允许动作、最大金额、审批要求、规则/原因码，以及拒绝或人工复核状态。
- **RefundRequest**：幂等退款业务对象。
- **ReturnRequest**：幂等退货/退货退款业务对象。
- **SupportTicket**：安全转人工对象，包含证据与原因。
- **ApprovalRequest**：高风险动作 Human-in-the-loop 权威审批状态。
- **AgentRun**：一次用户任务执行，拥有显式状态与最终结果。
- **ToolExecution**：一次 allowlisted 业务能力调用的结构化记录。
- **AuditLog**：重要业务/安全读写与决策的审计记录。

## 成功标准

- **SC-001**：评审者可以独立演示至少五条业务路径：物流异常退款、已签收退货、模糊订单澄清、高风险审批、安全转人工。
- **SC-002**：对同一句退款类自然语言请求，至少四种 seed state 能产生至少三种实质不同的下一步动作或 Tool Path。
- **SC-003**：所有资金/状态写入 Eval case 在业务系统接受写入前都经过确定性 eligibility/authorization。
- **SC-004**：最终安全评测集中，不接受任何跨用户写入或绕过审批的写入。
- **SC-005**：在重复提交、重试和未知超时场景下，每个逻辑退款/退货最多产生一次对应业务写入。
- **SC-006**：所有已完成 Agent run 都包含足够结构化 trace，可重建主要状态/Tool/审批/写入/验证路径。
- **SC-007**：项目包含版本化离线 Eval 集，不少于 60 例，目标约 74 例，并使用冻结 test split 做最终报告。
- **SC-008**：项目材料中报告的 Baseline 与 Agent 结果来自可比较评估条件，并能追溯到 dataset/run 配置。
- **SC-009**：60–90 秒 Demo 可以展示一条正常售后执行路径和一条安全/失败路径，并可见地证明系统改变了业务状态，或明确拒绝/升级，而不是只回答问题。
- **SC-010**：简历/README 中的成功率、时延、安全结果、成本或改进数字，在没有可复现 Eval Run 和指标定义前不得写成已达成结果。

## 假设与范围

- 第一版使用 synthetic/local 但 contract-realistic 的电商业务系统，不宣称真实生产支付或真实电商平台集成。
- V1 用户视为已经登录，完整注册/找回密码/社交登录不属于核心功能。
- V1 聚焦一个有边界的售后领域：订单识别、物流证据、退款/退货 eligibility、退款/退货请求创建、安全升级和一条人工审批路径。
- 商品推荐、售前 FAQ、商家运营、营销、采购、真实支付结算、全渠道客服、模型训练和 Multi-Agent 不属于 V1。
- 如果实现证明系统退化为固定的 `intent → refund endpoint`，且中间证据无法改变下一步动作，则本 Feature 的 Agent 价值假设失败；在增加更多技术之前必须重新设计。
