## 今天学到

- **重试资格由「方法安全性 × error 的 retryable 标志」共同决定，不是只看方法。** 完整对照：
  - `GET` → 403：`retryable=false`，重试一万次还是 403；
  - `GET` → timeout：结果未知但无副作用，可重试；
  - `POST` → 503（后端**答了**）：结果**已知**未提交，可重试；
  - `POST` → timeout（后端**没答**）：结果**未知**，必须先查权威状态。
  - 对称性一句话：**「答了」= 结果已知 = 重试安全；「没答」= 结果未知 = 写操作重试危险。** `timeout` 的全部麻烦都来自第二行。
- **`IdempotencyKey` 存在不等于可以盲目重试。** `tool-contracts.md` 的原话是"禁止 blind retry；未知 timeout 后先查状态；只有安全时才允许同 key 重试"。两个理由：① 必须知道已经发生了什么才能决定下一步；② **幂等键必须在重试之间保持不变** —— Agent 若每次重试重新生成 key，"重试"就变成第二笔退款。
- **`state.py` 里预留的 `WriteStatus.UNKNOWN` / `VerificationStatus` 正是 T016 要生产的值。** T015 与 T016 的连接点不是抽象的，就落在这两个枚举上。
- **`extra="forbid"` 与 `extra="ignore"` 是同一个问题的两个方向，选哪个取决于"这个对象是谁造的"。** `AgentState` 由**本服务**构造 → `forbid`（未声明字段是 bug 或注入）；Java 的响应由**别的服务**构造 → `ignore`（否则后端加一个字段就把健康响应变成解析失败）。同一条规则反向套用就是 bug。
- **HTTP 方法不等于语义。** `POST /after-sales/eligibility` 是 POST，但它是**确定性、无副作用**的评估，不是写操作。因此 `request_was_safe` 必须由**操作的语义**决定，不能写成 `method == "GET"` —— 否则这个"读"接口会被当成写操作，白白失去安全重试能力。

### 面试压缩（可直接讲）

> timeout 不等于失败，它只说明**我不知道**。所以读和写的处置必须不同：GET 是 safe 的，重试最多浪费一次调用；写操作可能已经提交，直接重试会重复执行 —— 必须先查权威状态。但更准确的规则是，重试资格由**方法安全性 × 错误的 retryable 标志**共同决定：GET 拿到 403 同样不能重试；反过来 POST 如果拿到明确的 503（后端答了、没提交），重试是安全的。还有一个常见坑：带幂等键不等于能盲目重试，**幂等键必须在重试间保持不变**，否则重试就变成第二笔退款。
>
> 追问预判：timeout 后不重试，用户看到什么？→ 不能转圈，要返回明确的"结果待确认"状态 + 可恢复路径（落到 `WriteStatus.UNKNOWN`）。幂等键谁生成、放 header 还是 body？→ 由发起方生成、随请求头传递，且跨越重试保持同一值。如果**查询本身**也 timeout？→ 受 retry budget 约束，耗尽后 safe stop，不能无限循环。
