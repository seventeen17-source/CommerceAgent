## 关键设计决策

### 1. 为什么是"行锁 + version CAS"而不是"二选一"

用户的 check point 选择是"行锁 + 事务内重读状态做 CAS"。实现后把两者的**分工**写清楚了，因为这是本题最容易讲错的地方：

- **`SELECT ... FOR UPDATE` 只负责串行化**。它让第二个请求**阻塞**，但阻塞不等于检测到过期。
- **如果只有行锁**：第二个请求醒来后会拿着自己读到的旧快照继续推进 —— 这就是 T017 要禁止的**分叉**。
- **version 比较才负责"发现我读到的那一行已经不是同一行了"**。
- 第 5 步 `UPDATE ... WHERE run_id = ? AND version = ?` 是**纵深防御**：即使锁被提前释放，过期写入也无法复活。
- **`READ COMMITTED` 就够**（PostgreSQL 默认）。反直觉但重要：在 `REPEATABLE READ` 下第二个事务会拿到 **serialization failure**，调用方就无法区分"基础设施报错"和"别人已经抢到这个 resume 了" —— 恰好丢掉 T017 要保留的赢家/输家信息。

### 2. 落表时的"漂移"防护

`data-model.md` §12 要求 5 个字段在行与 `state_json` 里同时存在且必须保持一致。落法：`_apply_transition()` 里**从同一个 dict 生成行值与 payload，且在同一条 UPDATE 里写入**。因此"行说 COMPLETED、payload 还是 RUNNING"在这个 store 里**不可表达**，而不是靠人记得。

同时 `COALESCE` 语义：调用方没设的字段保留原值（否则每一步都会抹掉上一步的 `intent` / `resolved_order_id`）。

### 3. retention 的两个 band（按"为什么结束"决定保留什么）

| 状态 | 保留 state | 保留 tool trace | 理由 |
|---|---|---|---|
| `COMPLETED` / `ESCALATED` | 7 天 | 否 | 结果已在 run 行上；step 级细节只在刚跑完时有价值 |
| `FAILED` / `SAFE_STOP` | 90 天 | 是 | 这才是 Eval 和人工真正会重新打开的 run；`run_id + step_index + trace_id` 就是把失败追回 Java 请求的线索 |

- `RUNNING` / `WAITING_*` **任何年龄都不动**。等待中的 run，其 checkpoint 就是产品本身；回收它等于把一个暂停的 run 变成不可恢复的 run。
- **retention 不是删除**：只清 `state_json` 与旧 trace，并打上 `checkpoint_compacted_at`。run 行（状态、final_action、error_code）永久保留 —— 删掉行会毁掉 research.md 决策 10 要求的审计链。
- 全部操作**幂等**（`checkpoint_compacted_at IS NULL` 守卫），因为 retention 是最典型的"跑一半被杀掉再重启"的作业。

  2. 破坏发生前先 `git add` 一次，成本近乎为零，收益是"随时能退回去"。这些文件当时是 untracked，所以只能靠记忆重写；

### 2. 我用 PowerShell 批量补丁脚本，制造了级联失败

- 脚本按顺序做 30+ 处 `Replace`，前面的替换改变了后面的匹配上下文 → 一半 `MISS`、一半 `已应用`，并且留下一个 `intent: str | None = (` 未闭合，**语法错误**。
- 更隐蔽的一层：判存在性用了 `-notlike "*$o*"`，而 `$o` 里含 `[` `]`，PowerShell 的 `-like` 把方括号当字符类 → **假 MISS**。
- 处置：改用 `Contains()`（字面匹配）+ 一次只改一处，并逐条校验。
- 教训：批量文本编辑**不要用"链式 replace"**；要么改一处验一处，要么用 AST/CST 级工具。

### 3. `create_run` 漏写了行上的投影列（真实功能缺陷，被集成测试抓住）

- 第一次跑真实数据库，`test_created_run_is_readable_with_version_one` 断言 `resolved_order_id == 'order-001'` 失败，实际是 `None`。
- 根因：INSERT 只写了 `run_id / user_id / status / state_json / model_*`，**漏了 `intent / resolved_order_id / step_count / retry_count`**。而这四列存在的意义正是"不反序列化 payload 也能按订单/意图查询"。
- 这正是**必须有真实数据库测试**的例证：它不是一个能被 mock 发现的错误，mock 只会重复我的假设。

### 4. V002 的 `completed_at >= started_at` 抓出了测试里的"跨时钟比较"

- Java schema 测试第一次写成：`started_at` 用数据库默认值（数据库时钟），`completed_at` 由 JDBC 传 `Instant.now()`（JVM 时钟）。数据库容器与 JVM 时区不同，相差 8 小时 → `chk_agent_runs_completion_time` 拒绝。
- 修法：让两个时间戳**出自同一个时钟**（都写 SQL 的 `CURRENT_TIMESTAMP` / `+ INTERVAL '1 second'`）。
- 价值：这不是"测试写错"，而是**跨时钟比较时间戳本身就不可靠**这个真实结论。

### 5. 本机 `localhost` 解析到 IPv6，而容器只绑定 IPv4 → 每个连接 5 秒

- 现象：集成测试每 2 个用例要 30+ 秒。
- 实测：`getaddrinfo("localhost")` 返回 `::1` 在前；而 `commerceagent-postgres` 只发布 `127.0.0.1:5432`。于是每次连接先等 IPv6 超时（`connect_timeout=5`）再回落 IPv4：**`localhost` 5.03s vs `127.0.0.1` 0.013s**。
- 处置：测试默认 URL 改 `127.0.0.1`，并在 conftest 写明实测数据。全套 21 个集成用例从"分钟级"变成 **1.55s**。

## 今天学到

- **"加锁"和"检测过期"是两件事**。锁解决"同时写"，版本号解决"我读到的是不是还是那一行"。只做前者在某些场景下反而更危险（阻塞后继续写旧快照）。
- **隔离级别不是越高越好**。`REPEATABLE READ` 会把"可裁决的业务冲突"变成"基础设施异常"，丢掉调用方需要的信息。
- **安全规则的检测点要少而固定**。逐字段白名单会腐烂；把规则挂在**操作**（"要落盘了"）上，新增字段默认被覆盖而不是默认开洞。
- **偶然的约束不是防护**：devlog 2026-09-18 记录的"64 字符 JWT 被 `max_length` 挡住"就是例子 —— 换个短凭据就穿透。
- **正则的误报和漏报要一起测**。这次专门为"普通英文句子"和"dotted trace id"写了不误报的测试；把"合法请求被拒"当成次要问题，是安全代码里最常见的取向错误。
- **集成测试抓的是假设之外的东西**。`create_run` 漏列、跨时钟比较、IPv6 连接延迟，三个都不是 mock 能发现的。

## T017 面试压缩

> Agent run 的持久化我拆成三份事实：run 行（可查询投影 + CAS 版本号）、checkpoint 历史（运行时状态的权威副本，可恢复）、tool trace（`run_id + step_index + trace_id`，把失败追回具体跨服务请求）。
>
> 并发 resume 是最关键的一处。要求是"同一旧 checkpoint 最多一个成功"。做法是在一个事务里 `SELECT ... FOR UPDATE` 锁行、重读 status 与 version、比较 caller 读到的 version、要求状态仍是等待中，最后 `UPDATE ... WHERE run_id = ? AND version = ?` 并要求影响一行。这里最重要的是**行锁只负责串行化，version 比较才负责发现过期**；只有行锁的话，第二个请求阻塞结束醒来后仍会拿旧快照继续执行，就是分叉。隔离级别我用默认的 `READ COMMITTED`，因为 `REPEATABLE READ` 会把冲突变成 serialization failure，调用方反而分不清"别人抢到了"和"数据库出错了"。
>
> 敏感信息防护不在字段上做，而在**持久化边界**做一次 fail-closed 全量校验，并且模型构造时也调同一个函数（一条规则挂两个点，不是两条规则）。检测用结构而不是数长度：JWT 必须前两段能解码成 JSON object，Bearer 后面必须是凭据形状 —— 因为旧正则会把 "bearer of" 这种普通英文判成凭据，而这个检查要用在用户输入上，误报的代价是"用户莫名其妙被拒"。
>
> retention 按"为什么结束"分 band：成功 run 7 天后只留 run 行，失败 run 保留 90 天且保留 tool trace，因为那才是会被复盘的对象；等待中的 run 任何年龄都不动，它的 checkpoint 就是产品本身。
