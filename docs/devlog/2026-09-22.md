## 今天学到（复验部分）

- **`VerifiedCredential` 只有 `issuer` / `expires_at` / `verified_at`，没有 `user_id`/`role`**：本地验签在类型层面就拿不到身份，所以“从 JWT claim 读 role 去授权”这个错误写法在本仓库写不出来。这是比注释更硬的约束。
- **JWT 的吊销空窗**：本地验签只证明“凭据是我的且未过期”，证明不了“这个人现在还是这个角色”。管理员降权/封禁后旧 token 仍可用到 `exp`，补偿手段只有短 TTL + 每请求读权威状态。权威侧读的是 `commerce.users` 的**当前**行，`role` claim 不参与授权。
- **权威侧返回的是“当前 userId + 当前 role”**，Run 的 owner 键用的是权威 `userId` 而不是 token 里的 `sub` 原串；`status`（封禁）不在 `/me` 响应里，而是在转换器里以 401 拦掉。
- 失败语义分三档不是洁癖：认证失败 → 401；权威服务不可达 → **503**（对认证正确的客户端说“你 token 坏了”既假又不可操作）。

## 关键决策（T019）

1. **越权读与"不存在"对外不可区分（统一 404 `ORDER_NOT_FOUND`，消息逐字相同）**。检测依据是 orderId 的可枚举性：fixture 是 `order-001`，扫描成本近零，403 会把"这个 id 真实存在"泄露出去（存在性预言机）。角色/能力级拒绝使用 `ACCESS_DENIED`；`ORDER_FORBIDDEN` 已删除。
2. **停滞基准取 `max(shipments.last_event_at, MAX(logistics_events.occurred_at))`**，两个来源都空则返回 `null`，**不回落** `orders.shipped_at`。理由分两层：技术层是投影列与事件表之间无约束防漂移；语义层是"物流停滞"的基准必须是物流事实，拿订单发货时间冒充物流证据会让证据看起来比实际更充分。

## 今天学到（T019）

- **"仓储方法名带 owner"是约定，不是强制**。`OrderRepository` 有 `findByIdAndOwnerId`，但它仍然 `extends JpaRepository`，`findById(String)` 这条后门一直可用且编译通过。**授权的最终把关只能在 service 层**；数据库层若要有强制力，需要行级安全（RLS），本项目没有。
- **403 与 404 的取舍是"多一个事实"与"好调试"之间的取舍**，不是对错题。403 的字面语义包含"资源存在"；当资源 id 可枚举时，这个附带事实本身就是泄露。面试里答"我们统一 404"要能说出**为什么**（可枚举性 + 无其他泄露渠道），否则只是背了一个结论。
- **`open-in-view: false` 让"Service 返回读模型"变成硬要求而不是风格偏好**：LAZY 集合离开事务就炸，所以 `OrderSnapshot` 必须在事务内组装完。
- **失败集合的形状比失败数量更能定位问题**：既有测试一起挂 → 环境；只有新测试挂 → 代码。这个判据在 CI 里同样适用。
- **`Clock` 的价值是"让依赖时间的逻辑变成可精确断言的函数"**，与"方便"无关。同理，任何"现在几点/随机数/当前用户"都应从外部注入——这三样是让测试变得不可信的常见来源。
- **契约也会自相矛盾**：`GET /orders/{orderId}` 声明 403+404，`GET /orders/{orderId}/logistics` 声明 403+503 却没有 404。实现者不该"静默挑一个"，而应把不一致作为发现报出来——本 T 报出来之后由用户拍板统一为 404 concealment，并把它写成**契约规则**而不是某一处的实现选择，这样 T023/T025 及以后的端点自动继承。
- **concealment 的判据是"标识符能不能被猜"，不是"这个端点看起来重不重要"**。同一个后端里，可枚举的 `order-001` 需要隐藏存在性，UUIDv4 的 `run_id` 则不需要——所以"订单用 404、run 用 403"不是不一致，而是同一原则在两个输入上的不同结论。面试里被问"你们越权返回 403 还是 404"，能答出这个判据比答出某一个取值高一档。
- **"对外抹平"之后必须回答"那内部还知道真相吗"**。如果答案是否，那么"有人正在枚举别人的订单"这件事将永远无法被回溯——concealment 是在**响应层**做的，不应该把审计能力一起抹掉。
- **隐藏与"隐藏失败"是两件事**：拒绝路径上的审计、日志、遥测一旦抛异常，就会用另一种形式把刚刚隐藏的信息（"这个 id 存在"）暴露出来。凡是"只在一条分支上执行的副作用"，都要问一句"它失败时会怎样"。
- **不要因为一个静态分析器告警就去改设计**：`OrderService` 注入具体类 `AuditWriter` 触发的 `EI_EXPOSE_REP2` 是**可证明误报**（private final、只用于调用、不出公开 API），正确处置是**最窄豁免 + 写清理由**；如果为了绕过它去造一个接口，那是让工具牵着设计走，而且会把一个真实的告警类型永久掩盖掉。

## 遇到的问题（T020）

- **"每条决策都必须带原因码"这条我一开始写的不变量是错的**，而且是被一个真实的用户场景逼出来的：当规则既没有声明停滞阈值、又没有审批阈值时（"无条件退款"这种规则），一条合法的**批准**决策会**没有任何**原因码可写，于是构造器自己抛异常、把一条有效的业务规则变成 500。处置是把它改成"**不批准**必须能解释自己，批准允许为空"——规则无条件时，解释已经在 `ruleCode + allowedAction + maxRefundAmount` 里，硬塞一个"条件已满足"的填充码只会变成 Trace 与 Eval 的噪声。教训：不变量要在**边界用例**（这里是"条件最少的那条规则"）上过一遍，否则它会以"保护数据一致性"的名义制造新故障。
- **测试隔离：别的测试类留下的规则行会让本测试红**。`AfterSalesRulePersistenceTest` 插入 `T010-ROUNDTRIP`（ELECTRONICS / SHIPPED / active）后**不清理**，而 `FixtureLoader` 的 `LOGISTICS_STALLED_REFUND` 也是 ELECTRONICS / SHIPPED；Spring 会缓存上下文，本测试类有可能与它们**共用一个容器**。三条 ELECTRONICS / SHIPPED 规则同时匹配同一订单时，按本 T 新写的语义正好命中 `CONFLICTING_RULES` → 转人工 → 本测试挂。处置是集成测试统一使用 T020 专属 `productCategory`。这既是隔离技巧，也说明**保守的冲突检测会把"环境里多出一行数据"放大成业务结论**。

## 关键决策（T020）

1. **"评估完成"与"评估无法完成"分成两条通道**（用户拍板）。`DENY` / `MANUAL_REVIEW` 是**成功的评估**，以 `200` 决策 + `reasonCodes` 表达；只有越权 `404`、规则前提冲突 `409`、依赖不可用 `503` 才是错误。判据不是"结论好不好"，而是"这次评估有没有跑完"。由此 `ELIGIBILITY_DENIED` / `MANUAL_REVIEW_REQUIRED` / `APPROVAL_REQUIRED` / `AMOUNT_EXCEEDS_ALLOWED` 被明确为**写路径**错误（提交前重校验拒绝一个 proposed action），已写进 `error-contracts.md`。
2. **没有适用规则 → `MANUAL_REVIEW` 决策且不引用规则**（而不是"随便挑一条"或"抛错误"）。代价是契约里 `ruleCode`/`ruleVersion` 必须放开为可空，并同步 Python 消费端。收益是"规则集无法回答"这件事保持了机器可读的子原因（`NO_APPLICABLE_RULE` / `ORDER_STATE_NOT_ELIGIBLE` / `CONFLICTING_RULES`），而不是只剩一个 errorCode。
3. **金额超规则上限 → `DENY`**（用户拍板）。`max_refund_amount` 是规则硬边界，不是 `approval_threshold` 那种"要人批一下"；V1 只支持整单退款，因此不做部分退款兜底。
4. **停滞时长未知 → `MANUAL_REVIEW`**（用户拍板），延续 T019 "`null` 是不知道，不是 0"。`DENY` 是"证明不符合"，`MANUAL_REVIEW` 是"无法证明符合"；US5 的人工升级路径依赖这个区别。
5. **决策拆成"纯函数 + I/O 外壳"**：`decide` / `selectRule` 不读时钟、不查库、不调服务，时间作为参数传入。这样"确定性"有了可执行证据（26 例 0.027 秒、两次调用 record 相等），而不是靠代码读起来像没有随机数。
6. **`evaluate(principal, orderId)` 不接收 `reasonCode`**：用户或模型的措辞不参与规则选择与金额计算。这不是"记得别用"，而是**签名里就没有这个输入**。
7. **契约字段关系搬进 `EligibilityDecision` 的构造器**：`eligible` 与 `allowedAction` 是冗余字段，靠约定维系必然漂移，因此把一致性强制成"矛盾的决策无法被构造"。其中批准动作**正向列举**（而不是"排除 DENY/MANUAL_REVIEW"），将来 Java 新增动作取值时默认是"没批准"。
8. **只收集规则要求的证据**：规则没声明停滞阈值就不读物流。否则一条不需要物流的规则会被一次物流依赖故障拖成 503，把可确定性回答的问题变成失败。
9. **保守的冲突检测**：两条不同 `ruleCode` 同时匹配同一订单 → 转人工，不任选。任选等于让 seed 数据的插入顺序决定用户能退多少钱。

## 今天学到（T020）

- **"拒绝"和"不知道"是两种业务结论，合并它们会把故障固化成政策**：一次 503 被降级成 `DENY`，用户就永久拿不到那笔退款，而且日志里看起来一切正常。
- **不变量是双刃剑**：构造器里的强约束能在编译/构造期消灭一整类"半真半假"的决策状态，但每一条不变量都必须先在**边界数据**上验证过。我这次的"必须有原因码"就是在"零条件规则"上翻的车。
- **纯函数是"确定性"唯一廉价的证明方式**：把 I/O 推到一个外壳里之后，决策矩阵可以在 0.027 秒内跑 26 条精确断言（含 47h/48h、299.99/300.00、500.00/600.00 这些决定钱的边界）。而依赖 Spring 上下文与真实数据库的 7 条集成用例只用来证明"规则来自权威表""ownership 口径被继承""依赖故障不被吞"这三件**只有真实存储才能证伪**的事。
- **契约放开一个字段会静默削弱一条既有断言**：`ruleCode` 变可空后，Python 里"缺 `ruleVersion` 必须报错"的用例自动失效（它会变成合法输入）。放开字段时必须回头逐个检查靠"这个字段必需"来证明事情的测试，否则断言会从"拒绝缺字段"悄悄变成"什么都不测"。
- **审查一个新端点时要问"它的权威失败模式声明齐了吗"**：`POST /after-sales/eligibility` 原本只有 `200/401/403`，但它现在要读订单（`404`）、读物流（`503`）并按规则前提判断状态（`409`）。契约缺项会在实现时变成"实现者自己发明语义"，这正是 T019 在 logistics 端点上抓到的同一类问题。
- **负向枚举会随枚举增长而失效**：`allowedAction != DENY && != MANUAL_REVIEW` 在新增第三个"不批准"取值的那天会静默放行。改成正向列举（`== REFUND_ONLY || == RETURN || == RETURN_REFUND`）后，新型取值默认落回"没批准"。

## 面试压缩（T020）

1. **资格与金额只能由确定性规则产生**：模型/用户的措辞连函数签名都进不来；规则从权威表按类目、订单状态、生效窗口筛选，同一 `ruleCode` 取最新版本，两条不同规则冲突时转人工而不是任选。
2. **拒绝模型要分清"证明不符合"与"无法证明符合"**：前者 `DENY`（停滞不够、超过规则上限、已有售后），后者 `MANUAL_REVIEW`（证据缺失、来源冲突、没有适用规则）；两者都不动钱，但对 Agent 的后续动作含义不同。依赖故障（`503`）绝不能被降级成任何一种拒绝。
3. **冗余字段必须被强制一致，而不是靠约定**：`eligible` 与 `allowedAction`、`reasonCodes` 与结论、`ruleCode` 与 `ruleVersion`，全部在构造期互锁；这样"决策说拒绝但带着可退金额"这种状态在系统里根本无法被表达出来。
