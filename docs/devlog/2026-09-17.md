## 遇到的问题

- **uv 官方文档描述的是 ≥0.12 的行为，本机是 0.11.28，实测不一致**：文档称应用模板默认定义 build system 并把源码放进 `src/`，但 0.11.28 实测生成的是根级 `main.py` 且**没有** `[build-system]`。结论：涉及工具版本的结论必须用本机 `--help` 与临时目录实测确认，不能只读文档。
- **命令行退出码不能作为唯一判据**：`uv add --dev` 之后整条 PowerShell 命令返回 `exit code: 1`，但 `pyproject.toml`、`uv.lock`、`.venv` 与导入 smoke test 全部正常。以产物为准。
- **控制台输出编码会污染判断**：PowerShell 输出中的中文会乱码，用 `Select-String` 匹配中文标题会静默失败，一度让我误判 devlog「只有 32 行」。判定文件内容必须用专用读取工具或 `git diff`，不能只看控制台输出。
- **PowerShell `Select-Object -First N` 会掐断上游管道**：用它筛选 `mvnw verify` 的输出时，Maven 在构建中途被 PowerShell 杀掉（`exit=-1`），看起来像构建失败，实际是我自己截断了管道。正确做法：先把完整输出落盘，再对文件做筛选。
- **本会话沙箱把 uv / npm 的缓存与 Python 安装目录挡在工作区之外**：uv 默认写 `%LOCALAPPDATA%\uv\cache` 与 `%APPDATA%\uv\python`，npm 缓存与 `~/.npmrc` 也在工作区外，`workspace-write` 下均被拒绝。为了让生成的工程与用户真实环境完全一致，相关命令使用了提权；最终 `.venv` 正确指向 `%APPDATA%\uv\python\cpython-3.13-windows-x86_64-none`。
- **`npm install` 首次以 `ECONNRESET` 失败，原样重试即成功**：失败信息为 `Invalid response body while trying to fetch https://registry.npmmirror.com/react-dom: read ECONNRESET`。事后用 Node 实测两个 registry（npmmirror / npmjs）均返回 200，重试亦成功，判定为**瞬时抖动而非配置错误**。启发式：**先确认可复现性，再动配置** —— 否则会为一个不存在的问题改动机器设置。
- **npm 原本没有配置代理**：`~/.npmrc` 只有 `registry=`，`proxy` / `https-proxy` 均为 `null`。按用户指示配置 `http://127.0.0.1:7892` 后 `npm ping` 稳定返回 `PONG 1326ms`。
- **Windows 默认执行策略会让 `npm` 直接不可用**：在 PowerShell 里敲 `npm run build` 报 `无法加载文件 E:\node\npm.ps1，因为在此系统上禁止运行脚本`。根因不是 npm 坏了，而是 Node 同时提供 `npm.ps1` / `npm.cmd` / `npm` 三个入口，PowerShell 优先命中 `npm.ps1`；而本机 `Get-ExecutionPolicy -List` 的所有作用域均为 `Undefined`，回落到 Windows 默认的 `Restricted`。
  - 绕过方式：显式使用 **`npm.cmd`**（`npm.cmd run build`、`npx.cmd`），零配置改动。
  - 永久修复需改机器安全策略（`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`），属安全策略变更，未经用户确认不做。
  - **对项目的意义**：默认 Windows 环境 clone 本仓库后，照 README 敲 `npm run build` **必然失败**。
- **PostgreSQL 18 官方镜像改了 `PGDATA` 与 `VOLUME`**：官方文档明确写「18 的 `PGDATA` 是 `/var/lib/postgresql/18/docker`，且 `VOLUME` 改为 `/var/lib/postgresql`，挂载必须指向新位置」。若沿用 PG17 及以下习惯挂 `/var/lib/postgresql/data`，数据会落到匿名卷，**容器重建即丢数据且毫无报错**。本次已按官方指引挂 `/var/lib/postgresql`。

## 今天学到

- **依赖的「声明」与「锁定」是两个文件，而且锁文件里还存着声明的副本**：`pyproject.toml` 写范围（`fastapi>=0.141.1`），`uv.lock` 写精确版本与哈希。`uv.lock` 内部 `specifier = ">=0.141.1"` 是**声明的指纹**，`version = "0.141.1"` 才是**锁定的事实**；判断时必须看对 `[[package]]` 区块的归属。
- **`--locked` 挡的是「声明漂移」，不是「结果漂移」**：实测把 `>=0.141.1` 放宽为 `>=0.141.0` 后，`uv sync --locked` 仍然报错 —— 尽管解析结果一个包都没变（`Resolved 58 packages`）。因为变的不是结果，是声明。
- **npm 与 uv 的语义对照**：

  | uv | npm | 语义 |
  |---|---|---|
  | `uv add` / `uv lock` | `npm install` | 允许重解析，**会更新 lock** |
  | `uv sync --locked` | `npm ci` | lock 必须与声明一致，否则**报错** |

- **`.python-version` 与 `requires-python` 不是同一件事**：前者是本工程实际使用的解释器版本，后者是项目声明的兼容范围（包元数据）。
- **TypeScript 的类型在产物中完全不存在**（type erasure，类比 Java 泛型只在编译期存在）。证据在配置里：`web/tsconfig.app.json` 有 `"noEmit": true`，说明 `tsc -b` **不产出任何 JS**，`build` 里的 `tsc` 只是类型检查闸门，真正把 `.tsx` 变成 `.js` 的是 Vite。
- **Vite 开发模式不是打包工具**：`vite dev` 用浏览器原生 ES modules 按需加载；只有 `vite build` 才把 20 个模块合成 `dist/assets/index-*.js`。
- **前端产物概念的对应关系**：`node_modules` ↔ `.venv`；`dist` ↔ `target`；`package-lock.json` ↔ `uv.lock`；`package.json` 的 `scripts` ↔ `pom.xml` 的插件配置；`tsconfig.json`（solution 文件）↔ Maven 多模块 aggregator pom。
- **权限边界必须用「拒绝证据」证明，而不是「配置里写了」**：T005 的核心验收不是"脚本里有 REVOKE 语句"，而是**实际用 `agent_app` 去读 `commerce.orders` 并拿到 `permission denied`**。同时配一个正向对照（该角色在自有 schema 能建表），排除"整个库都连不上"的假象。
- **一个实例 + 多个 schema 时，`owner` 就是语义归属**：`CREATE SCHEMA ... AUTHORIZATION <role>` 让"谁是这块数据的权威"变成数据库事实；配合 `ALTER DEFAULT PRIVILEGES`，之后 Flyway 建的表会自动落到正确的角色手里。
- **基础设施类改动必须先查官方镜像的破坏性变更**：PG18 的 `PGDATA`/`VOLUME` 变更不会报错、只会静默丢持久化 —— 这类"沉默的失败"比报错更危险。
- **`node --use-env-proxy` 可让 Node 内置 fetch 走 `HTTP_PROXY`/`HTTPS_PROXY`**：本机直连 Docker Hub API 超时，加上该 flag 与代理环境变量后即可访问（用于查 `pgvector` 镜像 tag）。
- **`docker compose config` 可离线校验 compose 文件**：不需要守护进程，就能验证镜像、卷挂载点、端口、healthcheck 是否符合预期。
- **配置分层要用 profile，而不是注释掉或写死**：`spring.profiles.default: dev` 的语义是"没有任何 profile 被显式激活时才生效"，正好让本机开发连真实数据库、而测试连 Testcontainers —— 同一份配置同时服务两种环境，且都不需要改文件。
- **同一数据库、两种身份**：Flyway（DDL 权威）与应用（DML 使用者）用不同角色，是"最小权限"在迁移场景下的具体落地。启动日志里能同时看到 `migrator` 建 `flyway_schema_history`、`commerce_app` 建 Hikari 连接池，就是这条设计在生效的证据。
- **pydantic v2 的 `model_` 保护命名空间**：字段名 `model_name` 会与 pydantic 的保护前缀冲突，必须在 `model_config` 里设 `protected_namespaces=()` 才能使用 —— 只有实测装载成功并读出 `gpt-4o-mini`，才算确认。
- **静态质量工具要能"只在有意义时失败"**：JaCoCo 先只出报告、不设阈值；等有真实业务代码后，再依据证据决定门槛。
