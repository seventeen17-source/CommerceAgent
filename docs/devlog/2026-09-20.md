## 遇到的问题

- **一个自己写的一次性脚本把质量门禁永久点亮成红。** `tmp_smoke_t016.py` 是活体冒烟脚本，docstring 里明写 "Delete after the session"，但它放在 `agent-service/` 包目录内，`ruff check .` 会扫到它 —— 19 个 lint 错误里 **14 个来自这个文件**（RUF100×7 / S101×6 / S106×1）。结果就是：删掉它门禁立刻回绿，但 agent 一直在改产品代码找原因。**这是"临时文件必须放在 lint 扫描范围之外，或者用完立刻删"的硬教训。**
- **HTTP 代理会悄悄劫持 Agent 的权威通道。** 首次活体冒烟时 httpx 从环境**和 Windows 注册表**解析到系统代理 `127.0.0.1:7892`：`http://localhost:8080` 被接管、**转发的 Bearer token 发给了第三方进程**、返回的还是契约外的 502（连错误信封都不是，会被归为"结果未知"）。修法是构造期 `trust_env=False`，把代理变成显式选择。

## 关键决策

- **`request_was_safe` 由操作语义决定，不由 HTTP 方法决定。** `POST /after-sales/eligibility` 是 POST，但它是确定性、无副作用的评估，所以标 `True`。写成 `method == "GET"` 不仅会让这个读接口失去安全重试能力，更糟的是会教会下一个人给 T026 的写端点也这么写 —— 而那里必须返回 `False`。
- **契约外的错误响应一律按"没有答案"处理。** 即使后端返回了 5xx，只要 body 不符合 error envelope，就归为 `CommerceTransportError`（结果未知）。裸状态码无法证明写操作没有提交，把它当"已知失败"等于为盲目重试发放许可。悲观，但不会不安全。
- **client 自己永不重试。** `retryable=true` 不是重试授权；retry budget 属于 Tool 层。在 client 里放重试循环，会把 unknown-outcome 这个案子从唯一有权决定处置的层眼前藏起来。
- **wire `role` 与 `allowedAction` 都保持开放字符串，未知值在身份层显式拒绝。** Java 拥有这两个值域，消费端镜像成 enum 会把后端的加法变更变成前端的解析失败 —— 而那是 run 根本创建不出来的失败形态，没有 `SAFE_STOP`、没有 reason code、没有审计记录。
- **`AuthContext` 刻意不含 `user_id`。** 它装的是**凭据**而不是**身份声明**；一旦带上 user id，调用方（或 bug、或经调用方转述的模型输出）就能"断言"身份而不是"证明"身份 —— 把字段拿掉，错误设计就不可表达了，比写文档劝阻可靠。
- **错误路径与成功路径必须共享同一套 trace authority。** 成功响应早已通过 `_correlate()` 对 `X-Trace-Id` 做格式/长度校验；如果错误响应再直接信任 JSON envelope 的 `traceId`，就会出现"成功路径安全、错误路径绕过校验"的分叉。现在统一以 `_correlate()` 的结果为准；envelope 中的值只用于契约一致性检查，不能覆盖最终持久化的 correlation id。

## 今天学到

- **`void` ≠ `Boolean`：JDBC 取一个 void 返回值，驱动不是返回 null 而是读空结果并抛类型转换错。** 这类错误的隐蔽性在于它只在某一条启动路径上出现（这里是 dev profile）。教训不是"记住这个函数签名"，而是 **`mvnw verify` 覆盖不到的路径必须有直接调用它的测试** —— 否则该路径等于没有测试。
- **"测试全绿"可能只是"这条路径从没被测过"。** T014 到 T016 之间所有 verify 都是 BUILD SUCCESS，而 dev fixture 初始化一直是坏的。
- **代理是安全边界的一部分，不只是网络配置。** 一个机器级代理就能拿到本服务转发的 Bearer token，而且它返回的错误还在契约之外。任何"我会把凭据发出去"的出口，都必须显式决定信任谁。
- **`timeout` 之后能不能重试，取决于"后端答了没有"**（结果已知 vs 未知）**乘以"请求有没有副作用"**，不是只看 HTTP 方法。

### 面试压缩（可直接讲）

> 我们做跨服务客户端时，把失败分成两种类型：后端答了（有错误信封，结果已知、没提交）和后端没答（超时/连接断，结果未知、可能已提交）。重试许可从这两个事实算出来，不是拍脑袋定的：答了就看 `retryable`；没答就只有无副作用的请求能盲目重试。这里有个容易写错的地方 —— 判定"有没有副作用"必须按**操作语义**而不是 HTTP 方法，我们有个 `POST /after-sales/eligibility` 其实是确定性评估，写成 `method == "GET"` 就错了。另外契约外的错误响应我们按"没有答案"处理：5xx 但没有规范错误体，不能假定它没提交。
>
> 追问预判：**为什么 client 自己不重试？** → `retryable=true` 不是重试授权，retry budget 属于 Tool 层；client 里放循环会把 unknown-outcome 藏起来。**token 怎么保证不进 prompt？** → 用 `SecretStr` 让 `repr` 脱敏，并且身份对象刻意不带 `user_id`，让"断言身份"这种写法无法表达。**为什么不用 enum 校验后端返回的 role？** → 那个值域归后端所有，镜像成 enum 会把后端新增一个合法角色变成我们的解析失败，run 直接创建不出来，连 SAFE_STOP 和审计都没有；正确做法是保持开放字符串，在身份层显式拒绝未知值。**代理和这事有什么关系？** → 有关系：我们实测到系统代理会接管请求并收到转发的 token，所以客户端 `trust_env=False`，把代理变成显式决策。
