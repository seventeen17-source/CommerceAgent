## 关键设计决策

### 1. 为什么是"行锁 + version CAS"而不是"二选一"

用户的 check point 选择是"行锁 + 事务内重读状态做 CAS"。实现后把两者的**分工**写清楚了，因为这是本题最容易讲错的地方：

- **`SELECT ... FOR UPDATE` 只负责串行化**。它让第二个请求**阻塞**，但阻塞不等于检测到过期。
- **如果只有行锁**：第二个请求醒来后会拿着自己读到的旧快照继续推进 —— 这就是 T017 要禁止的**分叉**。
- **version 比较才负责"发现我读到的那一行已经不是同一行了"**。
- 第 5 步 `UPDATE ... WHERE run_id = ? AND version = ?` 是**纵深防御**：即使锁被提前释放，过期写入也无法复活。
- **`READ COMMITTED` 就够**（PostgreSQL 默认）。反直觉但重要：在 `REPEATABLE READ` 下第二个事务会拿到 **serialization failure**，调用方就无法区分"基础设施报错"和"别人已经抢到这个 resume 了" —— 恰好丢掉 T017 要保留的赢家/输家信息。

### 2. 落表时的"漂移"防护

`data-model.md` §12 要求 5 个字段在行与 `state_json` 里同时存在且必须保持一致。落法：`_apply_transition()` 里**从同一个 dict 生成行值与 payload，且在同一条 UPDATE 里写入**。因此"行说 COMPLETED、payload 还是 RUNNING"在这个 store 里**不可表达**，而不是靠人记得。

同时 `COALESCE` 语义：调用方没设的字段保留原值（否则每一步都会抹掉上一步的 `intent` / `resolved_order_id`）。

### 3. retention 的两个 band（按"为什么结束"决定保留什么）

| 状态 | 保留 state | 保留 tool trace | 理由 |
|---|---|---|---|
| `COMPLETED` / `ESCALATED` | 7 天 | 否 | 结果已在 run 行上；step 级细节只在刚跑完时有价值 |
| `FAILED` / `SAFE_STOP` | 90 天 | 是 | 这才是 Eval 和人工真正会重新打开的 run；`run_id + step_index + trace_id` 就是把失败追回 Java 请求的线索 |

- `RUNNING` / `WAITING_*` **任何年龄都不动**。等待中的 run，其 checkpoint 就是产品本身；回收它等于把一个暂停的 run 变成不可恢复的 run。
- **retention 不是删除**：只清 `state_json` 与旧 trace，并打上 `checkpoint_compacted_at`。run 行（状态、final_action、error_code）永久保留 —— 删掉行会毁掉 research.md 决策 10 要求的审计链。
- 全部操作**幂等**（`checkpoint_compacted_at IS NULL` 守卫），因为 retention 是最典型的"跑一半被杀掉再重启"的作业。

### 3. `create_run` 漏写了行上的投影列（真实功能缺陷，被集成测试抓住）

- 第一次跑真实数据库，`test_created_run_is_readable_with_version_one` 断言 `resolved_order_id == 'order-001'` 失败，实际是 `None`。

- 这正是**必须有真实数据库测试**的例证：它不是一个能被 mock 发现的错误，mock 只会重复我的假设。

### 4. V002 的 `completed_at >= started_at` 抓出了测试里的"跨时钟比较"

- Java schema 测试第一次写成：`started_at` 用数据库默认值（数据库时钟），`completed_at` 由 JDBC 传 `Instant.now()`（JVM 时钟）。数据库容器与 JVM 时区不同，相差 8 小时 → `chk_agent_runs_completion_time` 拒绝。
- 修法：让两个时间戳**出自同一个时钟**（都写 SQL 的 `CURRENT_TIMESTAMP` / `+ INTERVAL '1 second'`）。
- 价值：这不是"测试写错"，而是**跨时钟比较时间戳本身就不可靠**这个真实结论。

### 5. 本机 `localhost` 解析到 IPv6，而容器只绑定 IPv4 → 每个连接 5 秒

- 现象：集成测试每 2 个用例要 30+ 秒。
- 实测：`getaddrinfo("localhost")` 返回 `::1` 在前；而 `commerceagent-postgres` 只发布 `127.0.0.1:5432`。于是每次连接先等 IPv6 超时（`connect_timeout=5`）再回落 IPv4：**`localhost` 5.03s vs `127.0.0.1` 0.013s**。
- 处置：测试默认 URL 改 `127.0.0.1`，并在 conftest 写明实测数据。全套 21 个集成用例从"分钟级"变成 **1.55s**。

## 今天学到

- **"加锁"和"检测过期"是两件事**。锁解决"同时写"，版本号解决"我读到的是不是还是那一行"。只做前者在某些场景下反而更危险（阻塞后继续写旧快照）。
- **隔离级别不是越高越好**。`REPEATABLE READ` 会把"可裁决的业务冲突"变成"基础设施异常"，丢掉调用方需要的信息。
- **安全规则的检测点要少而固定**。逐字段白名单会腐烂；把规则挂在**操作**（"要落盘了"）上，新增字段默认被覆盖而不是默认开洞。
- **偶然的约束不是防护**：devlog 2026-09-18 记录的"64 字符 JWT 被 `max_length` 挡住"就是例子 —— 换个短凭据就穿透。
- **正则的误报和漏报要一起测**。这次专门为"普通英文句子"和"dotted trace id"写了不误报的测试；把"合法请求被拒"当成次要问题，是安全代码里最常见的取向错误。
- **集成测试抓的是假设之外的东西**。`create_run` 漏列、跨时钟比较、IPv6 连接延迟，三个都不是 mock 能发现的。

## T017 面试压缩

> Agent run 的持久化我拆成三份事实：run 行（可查询投影 + CAS 版本号）、checkpoint 历史（运行时状态的权威副本，可恢复）、tool trace（`run_id + step_index + trace_id`，把失败追回具体跨服务请求）。
>
> 并发 resume 是最关键的一处。要求是"同一旧 checkpoint 最多一个成功"。做法是在一个事务里 `SELECT ... FOR UPDATE` 锁行、重读 status 与 version、比较 caller 读到的 version、要求状态仍是等待中，最后 `UPDATE ... WHERE run_id = ? AND version = ?` 并要求影响一行。这里最重要的是**行锁只负责串行化，version 比较才负责发现过期**；只有行锁的话，第二个请求阻塞结束醒来后仍会拿旧快照继续执行，就是分叉。隔离级别我用默认的 `READ COMMITTED`，因为 `REPEATABLE READ` 会把冲突变成 serialization failure，调用方反而分不清"别人抢到了"和"数据库出错了"。
>
> 敏感信息防护不在字段上做，而在**持久化边界**做一次 fail-closed 全量校验，并且模型构造时也调同一个函数（一条规则挂两个点，不是两条规则）。检测用结构而不是数长度：JWT 必须前两段能解码成 JSON object，Bearer 后面必须是凭据形状 —— 因为旧正则会把 "bearer of" 这种普通英文判成凭据，而这个检查要用在用户输入上，误报的代价是"用户莫名其妙被拒"。
>
> retention 按"为什么结束"分 band：成功 run 7 天后只留 run 行，失败 run 保留 90 天且保留 tool trace，因为那才是会被复盘的对象；等待中的 run 任何年龄都不动，它的 checkpoint 就是产品本身。

### 今日完成

### A. `app/security/credentials.py` — 入站凭据验证（**只证明"合法"，不证明"是谁"**）

- `VerifiedCredential` 是 `@dataclass(frozen=True)`，字段**只有** `issuer` / `expires_at` / `verified_at`。
  **没有 `user_id`、没有 `role`、没有 `sub`** —— 这不是省略，是设计：让"从 JWT claim 读 role 去授权"在类型层面写不出来。有专门的测试钉死这一点（`test_verified_credential_carries_no_identity`）。
- 四项检查，缺一项都是真实绕过：
  1. HS256 验签；
  2. **算法固定为 HS256**（绝不从 token header 读 `alg`）—— 这是 `alg: none` / RS256→HS256 混淆那个经典洞；
  3. issuer 必须匹配（同密钥但别的环境的 token 不能过）；
  4. **`exp` 必须存在且未过期** —— 没有 `exp` 的 JWT 永久有效，所以"缺失"是失败而不是默认值。`iat` **不**要求：它缺失只影响审计质量，不放大权限，而拒绝它反而会拒掉本项目 issuer 能产出的 token。
- 失败原因对**外**笼统（只说"凭据未被接受"），对**内**保留 `reason`。说清"签名对但已过期"会把接口变成 token oracle，而合法客户端自己能读 token。
- `MissingCredentialError` 与 `CredentialNotVerifiedError` 都是 401；`IdentityAuthorityUnavailableError` 是 **503** —— credential 可能完全没问题，是"解释它的权威"不可达。返回 401 会告诉一个认证正确的客户端"你的 token 坏了"，既假又不可操作。

### B. `app/security/dependencies.py` — 把"验证"接到"权威身份"

顺序即设计：**提取 → 本地验签 → 调 Java `/me` → `resolve_principal`（未知 role 拒绝而非默认 CUSTOMER）**。

- 返回 `AuthenticatedCall(auth, principal)`。handler 拿到的**没有** token 派生的 user id / role —— 想按 claim 授权也没有值可用。
- 本地验签失败 **不调 Java**（这是选 C 唯一买到的收益：省一次跨服务往返）。
- 认证声明在 **router 级**（`app/api/runs.py`），不是在每个 handler 上。**这是弥补 FastAPI 没有 SecurityFilterChain 的补偿控制**：新加的端点默认就是需要认证的，"忘记加 Depends"这个选项不存在。

### C. `app/api/runs.py` — 6 个 run 端点

- `POST /agent/runs`（201）、`GET /{id}`、`GET /{id}/events`、`GET /{id}/trace`、`POST /{id}/input`、`POST /{id}/resume`。
- **两个不同的问题、两个不同的状态码**，这是本文件刻意避免的混淆：
  - "**你有没有资格碰这个 run**" = authorization → **403**（存在但不是你的）/ **404**（不存在）；
  - "**这个 run 现在能不能被推进**" = state validity → **409**（带机器可读 reason）。
  - 顺序也有意义：**先鉴权再判状态**，所以不拥有该 run 的调用者无法通过 409 vs 200 探测它的状态。
- `create_run` 的三处边界：`run_id` 由服务端生成（不接受调用方指定）；`principal` 来自 `call.principal`（Java 的答案），请求体**没有**身份字段；**budget 从 settings 注入 state 并持久化**（T015 要求"恢复的 checkpoint 保留创建时的预算"）。
- `AgentRunView` 刻意**不返回 `state_json`**：里面有不可信用户输入和收集到的证据，UI 渲染不需要。
- `RunEvent` 由**已持久化的 checkpoint + tool trace 构建**，而不是内存事件总线 —— 重启后仍可解释，这正是 research.md 决策 10 的意义。

### D. `app/trace/store.py` 增补 `get_run_for_owner`（承接判断题 2）

- owner 进 **SQL 谓词**而非读后检查。两个后果都是理由：
  1. 别人的 run **根本不进本进程** —— `if record.user_id != owner` 同样正确，但要先把陌生人的 `state_json`（订单号、请求原文、证据）反序列化进内存再丢弃；
  2. **查不出错就忘不了**，没有"读—再鉴权"这对需要保持同步的动作。
- 因为 miss 天然有歧义，方法**显式消歧**：再问一次行是否存在，存在但不是自己的才报 `RunForbiddenError`。多一次查询换 403/404 诚实，契约要求如此。

### E. `app/main.py` — 应用入口

- lifespan 持有**进程级单例**：一个 `CommerceClient`（连接池）、一个 `PostgresRunStore`（无连接，只有工厂）。
- 挂在 `app.state` 而**不是模块全局**：模块全局会被 session 内每个测试共享，"让 app 用测试自己的数据库/transport"就做不到。
- `create_app(settings, *, commerce_client=None, run_store=None)` 是**工厂 + 依赖注入**：生产 `create_app()` 取环境配置，测试传入自己的，包括穿过 router 级依赖，**无需一份影子安全逻辑**。
- `/health` 报告 `jwt_secret_configured`（布尔，**绝不返回密钥**）：用默认密钥的服务看起来健康，直到有人伪造 token。

### F. 前端（判断题 A/3）

- `web/vite.config.ts`：dev proxy，`/agent` → `http://127.0.0.1:8000`（带 `rewrite` → `/api/v1/agent`），`/health` → 同目标。**同源，不需要 CORS 白名单** —— 把"允许任意源"这个误配置在生产里变成不可能。
- `web/src/App.tsx`：最小验证页（token 输入 + 请求文本 + 三个按钮 + 结果 JSON）。token 只放 React state，**不放 localStorage**。

### 遇到的问题（含 4 个真实缺陷 + 1 个环境陷阱）

### 1. `Depends(get_settings)` 与 app 自己的 settings 不一致（**同一个缺陷出现了两次**）

- 现象 A：所有已认证请求 401。根因：`get_settings` 是 `lru_cache`，而 `Settings(...)` **绕过缓存**，所以 router 级依赖 `authenticate` 解析到的是**环境** settings，而测试用自己签的 token。
- 现象 B（修完 A 之后才暴露）：run 建出来的 `max_steps=12`，而 app 是用 `max_steps=5` 构建的 —— T015 的"创建时注入预算"**静默不成立**。
- 根治：新增 `get_settings_from_app(request)` 从 `app.state` 读，**依赖与 handler 都用它**；`AppSettings` 别名定义在函数之后（`Depends` 要求 import 时名字已存在）。
- 这类缺陷**从外部看完全一样**，所以值得单独记：它长得像"认证坏了"，实际是"配置读错了"。

### 2. lifespan 覆盖了注入的协作者 → 测试打到了真实 Java

- `TestClient` 进入上下文时 Starlette **会真实执行 lifespan**，而 lifespans 里我**无条件**重建 `CommerceClient`，把测试注入的 stub 覆盖掉了。
- 后果：测试**打到了 :8080 上真实运行的 Java 服务**，而它用默认 dev secret，测试 token 是另一个 secret → 401。我一开始误判为"验签逻辑坏了"，查了 5 轮才定位。
- 修法：settings / commerce_client / run_store **三者都"已在 state 就用已存在的"**。
- 教训：**测试打到真实依赖上时，症状会伪装成被测代码的 bug**。这类问题值得在排查早期就验证"我到底在跟谁说话"（本次靠"stub 打不出日志 + 用一个独特的 userId 探针"确认）。

### 3. Vite proxy 少了 rewrite → 404（**正是端到端测试才抓得到**）

- `/health` 代理正常（无需 rewrite），但 `/agent/runs` 全部 404 —— 因为 app 注册的是 `/api/v1/agent/runs`。
- 修法：proxy 加 `rewrite: path.replace(/^\/agent/, '/api/v1/agent')`。
- 关键点：这个 404 **看起来像"路由没注册"**，而不是"代理路径不对"。单元测试永远看不到它。

### 4. 我自己的测试 fixture 差点变成破坏性清理

- 第一版 teardown 删的是 `SELECT run_id FROM agent.agent_runs WHERE user_id LIKE 'customer-%'` —— 对一个**共享开发库**执行，会删掉任何匹配的既有数据。
- 改成：只有通过 `create_run_via_api` 登记的 id 才会被删。
- 记录理由：**清理逻辑要删"自己造的"，不是"看起来像测试造的"**。同类风险在 T017 也出现过一次（我最初只想删自己的 uuid4）。

### 5. 环境陷阱：`localhost` 解析到 IPv6（与 T017 反向）

- T017 踩的是"**PostgreSQL 容器只绑 IPv4**，`localhost` 先试 `::1` 白等 5 秒"。
- T018 踩的是**反向**：本机 Vite dev server 只监听 **`::1`**（IPv6），所以 `http://127.0.0.1:5173/` **连不上**，必须用 `http://localhost:5173/`。
- 两者合起来说明**不能记住"用 127.0.0.1"或"用 localhost"这种口诀**，要按目标服务实际监听地址决定。这也解释了为什么"5173 端口连不上"时我的第一反应不该是"服务没起来"（它其实在 `::1` 上）。

### 6. 沙箱注意事项（非代码问题）

- `uv run` 在受限沙箱下无法写 `%LOCALAPPDATA%\uv\cache` → 用 `UV_CACHE_DIR=.uv-cache` 指到工作区内即可（`uv add pyjwt` 后已把该目录加进 `.gitignore`）。这比之前"改用 `.venv\Scripts\python.exe`"更好，因为文档里写的 `uv run ...` 四条门禁**原样可用**。
- 我上一段用过的 `-like`/链式 `Replace` 补丁脚本又坑了一次：`Set-Location` 不跨调用保持，导致脚本静默作用在错误路径上（`ReadAllText` 报 `DirectoryNotFoundException`，而 `$c` 为 null，后续 Replace 全部 no-op）。**每次 pwsh 调用都是新进程，不要依赖上一条命令的 cwd。**

### 关键决策

1. **本地验签只做快速失败，绝不做授权依据**：选 C 的安全风险不在"多一份密钥"，而在"验签通过 ≠ 有权操作"。用 `VerifiedCredential` 的**字段集合**把这条钉死，而不是靠注释。
2. **403 与 409 必须分开**：前者是"你有没有资格"，后者是"现在能不能推进"。混用会让调用方和 Eval 都分不清"越权"与"时机不对"。
3. **鉴权先于状态判断**：否则不拥有者能用 409 vs 200 探测他人 run 的状态。
4. **用 dev proxy 而不是 CORS 白名单**：不是省事，而是让"生产里允许任意源 + 带 Bearer"这个误配置**不可能**而非"不鼓励"。
5. **run 骨架刻意不做业务**：没有 LLM、不查订单、不退款。T018 的价值是**管道真实且有测试**，这样 T030 是往能用的管道里加行为，而不是同时调试管道和行为。

### 今天学到

- **"验证凭据"和"确定身份"是两件事**。前者可以本地做（快、省一次往返），后者的权威只能在业务服务那边。把两者混成一个 `get_current_user` 是最常见的退化方式。
- **`lru_cache` 的配置读取会和显式构造的配置静默分叉**，而且症状会伪装成别的问题（401、错误的预算）。**"这个 app 用的是哪份配置"必须只有一个答案。**
- **测试打到真实依赖上时，症状会伪装成被测代码的 bug**。先确认"我在跟谁说话"，再怀疑逻辑。
- **`localhost` 到底是 IPv4 还是 IPv6 取决于**谁在监听**，不是取决于你写了什么。T017（Postgres 只绑 v4）与 T018（Vite 只绑 v6）是两个相反方向的实例。
- **端到端测试抓的是"看起来像 A、实际是 B"的缺陷**：proxy 少 rewrite 表现为 404，会被误读成"路由没注册"。
- **清理逻辑只删自己造的**，不要用模式匹配去猜"哪些是测试数据"。

### T018 面试压缩

> Agent 接入层的认证我拆成两个不同的问题：**凭据是否合法**（本地用 HS256 验签、固定算法、校验 issuer 与 exp，失败直接 401、不调下游，省一次跨服务往返）和**这个凭据是谁、现在能不能做这件事**（只能由业务服务读权威用户表回答）。
>
> 关键设计是用**类型**而不是注释来防止退化：本地验签的返回值只有 issuer / expires / verified_at，**没有 user_id、没有 role**，所以"从 token claim 读角色去授权"在类型层面就写不出来。T011 已经定了 role 每请求从权威库读，本地 claim 一律不认。
>
> 另外两个我特意分开的东西：**403 和 409**。403 是"这个 run 不是你的"（鉴权，SQL 条件里带 owner，别人的 run 根本不进本进程），409 是"你的 run 现在不能 resume"（状态合法性，由状态机裁决）。顺序也必须先鉴权再判状态，否则别人能用状态码差异探测你的 run。
>
> 失败语义也分了三档：缺凭据/验签失败 401；权威服务明确拒绝 401；**权威服务不可达 503** —— 最后这条很重要，返回 401 会告诉一个认证正确的客户端"你的 token 坏了"，既假又不可操作。
>
> 5173 的串联测试抓到过一个只有端到端才能发现的问题：Vite 代理少了 path rewrite，`/agent/runs` 全部 404，而它看起来像"路由没注册"。同一轮还发现本机 Vite 只监听 IPv6，所以 `127.0.0.1:5173` 连不上必须用 `localhost` —— 和 T017 里 Postgres 只监听 IPv4 恰好相反。
