## 遇到的问题

- **`ddl-auto: validate` 第一次就抓出真实的类型不匹配（这正是它的价值）**：实体按默认把 `String currency` 映射成 `varchar(3)`，而 V001 建的是 `CHAR(3)`。启动直接失败：
  `Schema validation: wrong column type encountered in column [currency] in table [orders]; found [bpchar (Types#CHAR)], but expecting [varchar(3) (Types#VARCHAR)]`。
  修法是**让实体如实声明数据库的类型**（`@JdbcTypeCode(SqlTypes.CHAR)`），**绝不能反过来改已执行过的 V001** —— 那会让 Flyway 的 checksum 校验失败，`spring-boot:run` 直接起不来。
- **同一类问题的第二处**：`logistics_events.description` 在 V001 里是 `TEXT`，Hibernate 默认按 `varchar(255)` 期望，同样会被 validate 拦下。用 `@JdbcTypeCode(SqlTypes.LONGVARCHAR)`（PostgreSQL 方言下即 `text`）声明真实类型。
- **SpotBugs 抓到两条真实告警，而且逼出了更好的设计**：`OrderItem.getOrder()` 与 `LogisticsEvent.getShipment()` 报 `EI_EXPOSE_REP`（返回内部可变引用）。它的实际危害是：调用方可以 `item.getOrder().setStatus(...)` **绕过订单聚合根**改状态。修法不是加 `@SuppressFBWarnings` 压制，而是**只暴露 id**（`getOrderId()` / `getShipmentId()`）—— 顺带把聚合边界画得更干净。
- **ASCII 直引号混进 Java 字符串导致编译失败**：断言消息里写了 `（这正是"丢失更新"要防的事）`，其中引号是 ASCII 而不是中文弯引号，字符串被提前截断，`mvnw` 报 `需要')'或','`。改成不含内层引号的写法。**教训：中文文案里夹引号时，要么用「」，要么确认是弯引号。**
- **PowerShell `Select-Object -First N` 会掐断上游管道**（本会话已第二次踩）：用它过滤 `mvnw verify` 输出会让 Maven 中途被杀、`exit=-1`，看起来像构建失败。正确做法是先落盘再筛选。

## 今天学到

- **数据库约束的定位：它是"数据本身的规则"，不是"代码里的检查"**。代码里的 `if (exists) throw` 只管得住走这段代码的路径；DBA 手工 SQL、另一套服务、批量导入、并发线程都能绕过去。约束谁都绕不过。
- **四类约束一句话记住**：`NOT NULL` 不能空、`UNIQUE` 不能重复、`FOREIGN KEY` 不能指向不存在的东西、`CHECK` 只能是这几样之一 —— 本项目 V001 里四类全都用上了。
- **PRIMARY KEY = UNIQUE + NOT NULL，且每表只能有一个**。所以"主键能防重复"是对的，但它只防**自己那一列**：
  - 实测：`demo_pk` 表里 `id` 是主键、`order_id` 是 UNIQUE。插 `('S-9','O-1')`（新 id、重复 order_id）时，**主键完全满意，是 UNIQUE 把它拦下的**。若只有主键没有 UNIQUE，两条不同 id 就能指向同一订单 —— 于是"改哪个、删哪个、查哪个"全都没有答案。
  - 两者的实际差异：主键**不允许 NULL**（实测报 not-null violation），UNIQUE **允许 NULL 且多个 NULL 共存**（实测两行 NULL 都插入成功）。后者意味着：**幂等键若可空，唯一约束形同虚设**。
- **"先查再插"在并发下不够（TOCTOU）**：`SELECT ... 不存在` 与 `INSERT` 之间有时差，两个事务都能通过检查然后都插入。这个洞**只能由能仲裁并发的组件（数据库）来堵**。
- **两种失败必须分清，对策不同**：丢失更新（同一行被覆盖）→ 乐观锁 `@Version`；重复创建（插进两行）→ 唯一约束。**"改了"和"插了"是两件事。**
- **`ddl-auto: validate` 是一个免费的映射预言机**：它把"实体与数据库不一致"在**启动时**暴露，而不是等到运行时 500。今天它一次抓出 `CHAR(3)`、一次抓出 `TEXT`。
- **静态分析工具的正确用法是改设计，不是加注解压制**：`EI_EXPOSE_REP` 指向的是"聚合根引用被泄漏"，压制它等于把问题留在代码里。

### T009 面试知识点（检查点结论）

> **`@Version` 乐观锁防的是「丢失更新」，不防「重复插入」。**
>
> 原理：乐观锁靠"读到的版本号"作为暗号，UPDATE 时带 `AND version = ?`，影响 0 行就说明有人先改过。而并发**插入**的两个事务各自插入新行，版本号都是初始值，**没有共同的暗号可比**。
>
> 所以"同一笔退款只能有一条"必须靠**数据库唯一约束**（建在业务幂等键上）。重复请求到达时，捕获唯一约束冲突 → **回查已有记录 → 按成功返回**，而不是报错：重复请求不是错误，是同一逻辑操作的重放；返回错误会让调用方误判成功与否，在资金场景里更危险。
>
> 一句话分工：**乐观锁管"更新冲突"，唯一约束管"重复创建"，幂等处理负责"冲突时返回什么"。**
>
> 常见追问：乐观锁冲突后能不能重试？（写操作不能盲目重试，必须先查权威状态）`REPEATABLE READ` 能替代它吗？（不能，隔离级别不阻止丢失更新）唯一约束冲突怎么翻译成业务响应？（这就是幂等实现的核心）

### T015 review findings 处置结果

代码评审提出 3 点可改进项；没有照单全收，逐条判断后**全部在 T015 内收口**（不留模糊待办），处置结论如下：

1. 有界取值集目前是裸 `str`（`EligibilitySnapshot.allowed_action`、`ApprovalSnapshot.status`、`WriteOutcome.error_code`、`ToolHistoryEntry.error_code`），可考虑改成 `StrEnum`，让非法取值在构造期就失败。
2. `current_node` / `next_action` / `final_action` / `model_*` / token 计数 / 时间戳属于 **T017 持久化字段**，不属于 `AgentState` 运行时 schema —— 这个边界目前只写在实现者的脑子里，需要写进注释或 data-model。
3. `max_steps=12` / `max_retries=2` 是硬编码默认值，可考虑移入 `app/config/settings.py`，使其可配置、可被 Eval 覆盖。

**处置：**

1. **① 拒绝 + 文档化（这是本次最有价值的一次判断）。** 评审建议把远程拥有的取值集收成 `StrEnum`，实际判断后**不采纳**，理由：
   - `AllowedAction` 的取值集**已经有三份**（`AllowedAction.java`、V001 的 `chk_after_sales_rules_allowed_action`、`data-model.md`），Python 再镜像一份就是第四份，多一个漂移点。
   - 严格镜像会把 Java 侧的**加法变更**（新增合法动作）变成 Python 侧的**破坏性变更**：新值到达时 `ValidationError`，且如果 client 不专门处理就退化成未捕获异常/500 —— run 根本创建不出来，没有 `SAFE_STOP`、没有 reason code、没有审计记录。
   - 它强迫 **consumer-first 部署顺序**（先扩 Python 再让 Java 发新值），两个服务不再能独立发布。
   - 它让"对方新增了值"和"数据被写坏"变成**同一种错误**，失去可观测性。
   - 落法：`state.py` 模块级新增 **cross-service value policy**，明确"只有本服务拥有、必须穷举分支的集合才用 `StrEnum`"，并在 `allowed_action` / approval `status` / 两处 `error_code` 上各写明 owner 与未知值策略（未知值必须受控降级为 `SAFE_STOP` + reason code）。**下一个人看到裸 `str` 时不会再来"顺手修好"。**
2. **② 采纳，且比原描述更重。** 核对 V001 后发现 `agent.agent_runs` 行与 `AgentState` 是三种关系：**只在行里**（`current_node` / `next_action` / `final_action` / run 级 `error_code` / `model_*` / token 计数 / 时间戳）、**两边刻意重复**（`status` / `intent` / `resolved_order_id` / `step_count` / `retry_count`）、**只作引用**（`user_id` / `resolved_order_id`）。落法：`state.py` 增加 persistence boundary 说明，并在 `data-model.md` §12 补两条规则。
3. **③ 采纳，但改了"移法"。** 新增 `settings.agent_max_steps` / `agent_max_retries`；**没有**让 `AgentState` 用 `default_factory` 去读配置，理由是：①那会让数据 schema 反向依赖配置系统（等价于 JPA 实体里 `@Value` 读配置）；②恢复 checkpoint 时会静默采用今天的配置，让一个按旧预算运行的 run 突然越界。最终采用"schema 给安全兜底默认值 + 组合根（T017/T018 run 创建）注入配置值"，并明确 **restored checkpoint 保留创建时的预算**。

**④ 顺带发现的新问题（不在原 review 里）**：行与 `state_json` 重复的那 5 个字段是**漂移风险点** —— 行写 `COMPLETED`、payload 仍是 `RUNNING` 就是一种"看起来完成、恢复出来没完成"的假证据。已在 `data-model.md` §12 写成约束：**T017 必须在同一次写入里保持一致**。
