## 关键决策

- **故障注入放在 Agent 面向的 HTTP 边界，而不是 service 层或"删数据"**：这样 Agent 面对的是真实的错误信封（`DEPENDENCY_UNAVAILABLE` / `retryable=true`），而"数据缺失"是另一种事实（`LOGISTICS_UNAVAILABLE`），不能互相冒充；同时**生产类一行未改**，且故障不可能在生产 profile 被打开。
- **两个场景共用一个"可写世界"**：否则"没有退款行"只证明世界不可写，不证明 Agent 拒绝猜测（T042 记录过这个假通过）。
- **故障在 reset 前清空、成功后装载**：失败的 reset 不能留下一个"上一轮的故障"继续害人。
- **断言终态原因读 checkpoint，不读 run view**：读"系统真正记录了什么"，而不是"我以为它会记录什么"。
- **审计行纳入机器断言**：工单与审计同事务是设计承诺，只有断言过才叫证据。

## 今天学到（可面试）

- **HITL/失败恢复的"证据三段论"**：*结果*看权威业务行（ticket/refund/return），*机制*看 `agent.tool_executions`，*原因*看 checkpoint 的 `reason_code` —— 三者缺一，Gate 就会退化成"API 200"或"模型说它做到了"。
- **`SAFE_STOP` ≠ 失败**：它是系统主动的"不猜"决定，所以既没有 `errorCode`，也不该有业务写入；把它当成"调用失败"来断言或埋点，都是把安全能力误记成缺陷。
- **故障注入的层次感**：注入在越靠近边界的地方，越能证明"契约层"的行为；注入在越深处，越能证明"内部依赖处理"。两者不可互相替代，必须写清这次证明了哪一层（本数据集的边界已写进 yaml 头注释）。
- **环境问题 ≠ 代码问题**：`.git` 被沙箱保护、缓存目录被拒、Testcontainers 需要命名管道 —— 这三种都在本次真实发生过，且都在"看起来像代码坏了"的外表下。
