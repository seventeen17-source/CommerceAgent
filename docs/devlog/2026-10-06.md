## 追加：T036 负例修好之后才看见的那个洞（US2 直接退款守卫）

### 目标（追加）

用户指出：T036 的负例应当用**尚无售后动作**的 `DELIVERED` 订单，并断言**具名拒绝原因**；同时 Java 侧必须禁止它被 `REFUND_ONLY` 放行。补做这两件事并跑完整门禁。

### 关键发现：断言"为真"不等于"被执行过"

负例的夹具（`seedOrder`）把每张订单都写成 `afterSalesStatus = REFUND_REQUESTED`。于是决策在 `decide` 的第一步就以 `ORDER_ALREADY_HAS_AFTER_SALES` 返回 —— 断言 `!(eligible && REFUND_ONLY)` 当然为真，**而它声称要守的那条路（规则在 DELIVERED 上授予 REFUND_ONLY）从未被走到**。夹具撒谎，测试变绿，真正的守卫缺席也没人发现。

把夹具改对（`afterSalesStatus = null`）后立刻暴露真实漏洞：`evaluate(...)` 返回 **`eligible=true` + `allowedAction=REFUND_ONLY`** —— 一张已签收的订单可以被直接退款。原因是 `REFUND_ONLY` 分支只在规则**声明了停滞阈值**时才做冲突检查，而这条规则没声明，`needsLogisticsFacts` 因此为 false，流程直接走到成功决策。

### 修了什么

1. **负例夹具改对**：`DELIVERED` + 无任何售后动作；断言 `eligible=false`、`allowedAction != REFUND_ONLY`、`grantsMoneyAction()==false`，并断言**具名原因码** `DELIVERED_ORDER_IS_RETURN_ONLY`。
2. **新增 Java 守卫** `EligibilityService.deliveredOrderCannotTakeADirectRefund(order, action)` = `action == REFUND_ONLY && order.status() == DELIVERED`：
   - 判据取**订单生命周期状态**（权威、一定有值），不取运单：这里可能没有运单行，而"签收"在别处也是 `signedAt != null || status == DELIVERED`（`LogisticsStallCalculator.isSigned`）。
   - 它是**唯一判据**，被外壳（`needsLogisticsFacts`：决定要不要读物流）与决策层（产出哪个原因码）共用 —— 两处各写一遍条件迟早漂移。
   - 守卫排在停滞检查**之前**：对已签收订单，"停滞够不够"没有意义，先答它只会给出误导性的 `LOGISTICS_CONFLICTS_WITH_ORDER`（那描述的是"订单说 SHIPPED、运单说已签收"）。
   - 结论是 `DENY` 而不是 `MANUAL_REVIEW`：转人工等于把"给已签收订单直接打款"放进人工队列，而它正是 US2 要禁止的事；硬拒绝不动钱，并给客户一条可执行出路（走退货）。
3. **两条纯函数用例**（0.05 秒，不连库）：守卫本身；以及"这条路径连物流都不去读"。

### 变异检查（证明守卫是承重的）

把判据临时改成 `return false` 再跑 `EligibilityServiceTest`：**恰好这两条新用例红**（一条直接显示 `eligible` 变 `true`），其余 **30 条全绿** ⇒ 守卫既必要、又不误伤别的行为。随后立即还原。

### 缺陷一：T039 遗留的 500（新用例抓到的）

`decide` 无条件把 `refundableAmount` 塞进 `EligibilityDecision`，而它的不变式禁止"纯退货动作带金额" → **任何成功的纯 `RETURN` 决策都会抛 `IllegalArgumentException`（500）**。演示数据里的 `DEMO_HOME_30D_RETURN` 正好是纯 `RETURN` 规则，也就是这条路径在真实环境里"一调用就 500"。T039 当时的用例全落在 `RETURN_REFUND`（会动钱）或"注定被拒"的分支上，所以没暴露。
修法：金额与审批阈值只对会动钱的动作（`REFUND_ONLY` / `RETURN_REFUND`）生效；纯退货直接以"无金额、无审批"批准。
**可迁移的教训**：一个动作类型有两套语义时，"只测其中一条成功路径"等于另一条从没被测过。

### 缺陷二：契约文件里有四份不同的 `components`

`commerce-api.openapi.yaml` 有 4 个 `components:` 块（424 / 665 / 897 / 1134 行），块长 241 / 232 / 237 / 217 行、sha 各不相同。按 YAML 语义重复键通常"后者生效"，因此**有效定义取决于读者用哪份**。本次 schema 改动同步写进了全部 4 份（避免再添分叉），但根治要单独立任务：先决定以哪份为准，那是改契约语义的工作。已记入 `PROJECT_PROGRESS.md` 未决项。
