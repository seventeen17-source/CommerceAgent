# Phase 0 Research: 求职导向的 Agent 项目决策与设计

**Research date**: 2026-09-15  
**Purpose**: 解决规划方法、证据质量、评分不确定性和 6～8 周范围控制问题。本文中的岗位观察是规划前的初步核验，不等同于后续 Contract 1 要求的 30 条去重岗位市场报告。

## Decision 1 — 以早期人才岗位为主样本，生产岗位只作参照

**Decision**: 核心样本只纳入中国大陆校招、实习或明确 0～2 年经验的 Agent/LLM 应用工程岗位；社招生产岗位最多占扩展参照组的 20%，并与主样本分开统计。纯预训练、RLHF、CUDA、推理内核、销售方案和产品岗位排除。

**Rationale**: 用户目标是 2027 届应用工程求职，高级或算法研究岗位的高频技能不能直接代表其筛选门槛。初步核验已经显示同一“Agent”标题下至少存在应用全栈、平台后端、算法/后训练、搜索/RAG、评测与多模态等不同轨道。

**Alternatives considered**:

- 把所有包含 Agent 的岗位放在同一频次表：拒绝，因为会把训练算法和高级生产经验错误投射到校招项目。
- 只看校招：拒绝，因为样本可能过少，且无法了解企业生产成熟度；改为把社招独立作为参照。
- 用技术媒体或课程目录替代 JD：拒绝，只能作为解释材料，不能作为招聘频次证据。

## Decision 2 — 使用分层来源与可审计去重

**Decision**: 来源按 A～D 分级：A 为企业官方职位详情；B 为企业官方校园/团队招聘页；C 为高校就业中心完整转载且可追溯企业投递入口；D 为聚合页，仅用于发现线索。核心技能统计以 A 为主，必要时纳入可验证的 C；B 不含完整 JD 时只证明招聘方向；D 不进入核心分母。

建议至少覆盖 8 家雇主，每家最多 5 条核心记录。优先使用 `company + official_job_id` 去重；无职位 ID 时使用“规范化公司 + 部门 + 标题 + 招聘批次 + 职责文本指纹”。同 JD 多城市合并，同标题但职责显著不同则保留。

**Rationale**: 转载、内推镜像和多城市复制会造成伪高频。按独立雇主数判断置信度，比单纯按职位条数更能抵抗单一招聘网站或单一公司样本偏差。

**Alternatives considered**:

- 只按 URL 去重：拒绝，同一 JD 常有多个链接和城市镜像。
- 只按标题去重：拒绝，相同标题的部门和职责可能不同。
- 自动相似度直接合并：拒绝；文本高度相似只能触发人工复核，不能独立决定删除。

## Decision 3 — 能力结论必须保留职责语境和证据强度

**Decision**: 每项能力分别记录硬性要求、加分项、实际职责出现、岗位族分布和企业让其解决的问题。结论置信度按独立雇主交叉支持计算：至少 4 家雇主且 6 条核心样本为高；2～3 家或 3～5 条样本为中；单一雇主、团队或仅社招参照为低。

**Rationale**: “出现过”并不等于“校招硬门槛”，框架名也不等于底层能力。候选项目更应映射 Tool/API 调用、工作流、评估和业务落地等职责，而不是最大化技术关键词数量。

**Alternatives considered**:

- 只做词频：拒绝，无法区分硬性要求、业务职责和加分项。
- 将所有公司等权：拒绝，仍须限制单一雇主样本数并报告公司覆盖。
- 由初步样本直接定技术栈：拒绝，完整 30 条样本和候选比较尚未完成。

## Preliminary Market Signals — 仅用于验证研究方向

以下是一手招聘页面的初步事实检查，尚不能替代完整样本包：

- 字节跳动 Seed 2027 校招/实习公开方向包含 Code Agent、长程任务、Memory、Search Agent、多模态 Agent 和复杂 Agent 环境的系统优化，但不少岗位明显偏研究或 Agent RL，应与应用工程轨道分离。[Seed 2027 校招](https://seed.bytedance.com/zh/seedearlycareer)；[官方公告](https://seed.bytedance.com/zh/blog/bytedance-seed-2027-foundation-model-campus-recruitment-is-now-open-internships-included)
- 百度 2027 校招“Agent 应用全栈工程师”明确涉及 Planning–Acting–Reflection、Tool/API、Memory、状态管理、多 Agent、RAG+Agent，以及成功率、稳定性、Token/调用成本、延迟和体验评测；职位还接受课程或自发 Agent 项目作为经历证据。[百度职位 J99974](https://talent.baidu.com/jobs/detail/GRADUATE/6f9c3a86-6557-409d-8fa7-e6f4c68d6765)
- 百度校招“大模型研发工程师”更接近应用工程，涉及 Python、大模型 API、RAG/Agent/Prompt、推理服务、数据管道、性能和稳定性，容器与集群能力是加分项而非所有项目的默认必需。[百度职位 J100834](https://talent.baidu.com/jobs/detail/GRADUATE/7952a5bc-816a-4b9b-bd58-65d70a66d5d0)
- 百度 Agent 算法实习岗强调把业务问题转成可求解、可执行、可验证任务，并构建数据接口、求解器、仿真器、checker 与自动评测环境。这支持“评估闭环比 Demo 更有区分度”的规划判断，但该岗位属于算法轨道，不能直接代表应用岗全部要求。[百度职位 J103893](https://talent.baidu.com/jobs/detail/INTERN/9a8dca22-cdc4-4df9-99b6-58b2033b434b)
- 百度其他 Agent 算法/智能体岗位同时出现 router、plan、RAG、工具调用、训练方法、成本与效果评估，证明必须按岗位轨道拆分，而不能生成一份“全部都要学”的清单。[百度职位 J101345](https://talent.baidu.com/jobs/detail/INTERN/1a0bfe96-f59c-4384-9525-79fdf324c67f)；[百度职位 J101017](https://talent.baidu.com/jobs/detail/GRADUATE/02f73086-be71-4d09-8d6e-f1c6981b8b48)
- 京东公开职位体现生产参照信号：一类偏 Agent RL、Plan-Act、Generate-Verifier、Multi-Agent，另一类偏高并发、高可用、可复用中台和业务落地；页面未明确为校招，因此只进入参照组。[算法工程师](https://zhaopin.jd.com/web/job-info-detail?requementId=219373)；[Agent 开发工程师](https://zhaopin.jd.com/web/job-info-detail?requementId=219990)

**Preliminary inference**: 当前较稳定的项目规划方向是“真实业务任务 + Tool/API 执行 + 可验证评估 + 可靠性/成本/延迟可观测”；状态、记忆、规划、反思、多 Agent 和训练方法应由具体场景或岗位轨道决定，不能作为默认堆栈。安全、权限和审批具有工程区分度，但当前初步早期岗位样本不足以宣称其为普遍硬门槛。

## Decision 4 — 先过致命门槛，再进行加权评分

**Decision**: 所有候选先检查需求证据、Agent 必要性、企业真实性、两周纵向切片、8 周可交付、可评估、安全闭环和依赖可控性。任一项失败时只能淘汰或进入 4～8 小时的限时验证，不能依靠其他维度高分补偿。

通过门槛后，才按用户固定权重计算六维总分：需求 25%、Agent 深度 20%、面试内容 20%、可完成性 15%、基础匹配 10%、差异化 10%。

**Rationale**: 加权模型允许“高需求”补偿“无法评估”或“依赖拿不到的企业账号”等致命缺陷，因此必须使用非补偿式门槛。

**Alternatives considered**:

- 总分最高自动获胜：拒绝，无法处理致命风险。
- 临时改变权重来惩罚风险：拒绝，破坏用户指定权重和重算透明度。
- 只凭负责人主观选择：拒绝，无法复核且容易迎合热门概念。

## Decision 5 — 使用统一锚点、分数区间与敏感性分析

**Decision**: 六个维度使用 1、3、5、7、9 五档锚点，偶数代表相邻档之间；10 分只用于有异常强证据的例外。每个分数同时保存中心值、可辩护区间、证据等级、引用和改变分数的新证据。

证据等级默认对应不确定范围：A 多条近期一手证据（约 ±0.5）；B 多来源但覆盖有限（约 ±1）；C 主要由相邻岗位或设计推断（约 ±1.5）；D 未验证假设（约 ±2）。该映射是提示，不替代人工判断。

如果第一、第二名中心分差小于 0.5，或加权区间明显重叠，则不得宣称确定胜出；先做一个 4～8 小时的验证实验，例如验证关键数据/接口、跑通薄工具闭环、标注 10～15 条评估样本，或复核 JD 职责映射。

**Rationale**: 单点分数会制造虚假确定性；区间和低成本实验能把争论转化为可验证问题。

**Alternatives considered**:

- 增加更复杂的数学模型：拒绝，输入证据质量才是主要限制。
- 平局时凭差异化维度决胜：拒绝；差异化只有 10% 权重，不能覆盖交付或需求不确定性。

## Decision 6 — 三角色独立反证，并保留审计链

**Decision**: 面试官、招聘经理和实际开发者先各自写“淘汰备忘录”，再集中处置。每条问题记录严重度 P0/P1/P2、证据、失败场景、替代候选、建议删除项、验证方法和处理结果，并保存“原分 → 风险 → 处理 → 新分”。

- 面试官检查是否教程复刻、能否追问、指标是否可信、核心机制能否本人重写。
- 招聘经理检查业务价值能否 30～60 秒理解、是否映射目标职责、是否有更合适替代。
- 开发者检查数据、集成、调试、安全、成本和时间估计是否真实，识别技术堆砌。

P0 未解决则淘汰；P1 必须有裁剪、验证或替代方案与完成周次；P2 不能挤占核心范围。若首选失去门槛、保守分低于第二名，或只能通过扩大范围自救，则改选。

**Rationale**: 独立反证降低从众和首因偏见；保留原始异议而不只保存最终结论，能为面试提供真实取舍材料。

**Alternatives considered**:

- 只写一段“优缺点”：拒绝，缺少角色冲突、严重度和处置责任。
- 仅对第一名反证且不比较替代：拒绝，无法判断是否应改选。

## Decision 7 — 采用 6 周证据核心 + 2 周缓冲/包装

**Decision**: 核心按 6 周、约 90～150 小时设计；第 7～8 周用于缓冲、故障深度、复现实验和求职包装，不能成为核心 Demo 的依赖。第 1 周冻结 Must，第 2 周后不得新增 Must；错过门槛时削减范围而不是自动延期。

**Rationale**: 固定时间、可变范围和明确 circuit breaker 能防止学生项目把所有证据工作挤到最后。该决策借鉴 Basecamp 对固定 appetite 与 scope hammering 的公开方法，但周次门槛是针对本项目的适配，不是来源原文的直接规定。[Shape Up: Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)；[Decide When to Stop](https://basecamp.com/shapeup/3.5-chapter-14)

**Alternatives considered**:

- 8 周持续加功能：拒绝，没有恢复、评估与面试包装窗口。
- 前半程学理论/搭后端，后半程才做 Agent：拒绝，太晚暴露最关键集成风险。
- 6 周计划但没有缓冲：拒绝，无法应对模型、外部服务和学习曲线的不确定性。

## Decision 8 — 周计划使用纵向切片门

**Decision**:

| Week | Exit gate |
|---:|---|
| 1 | 业务结果、当前基线、Agent 必要性、工具/场景契约、评估模式、最大未知与削减规则冻结 |
| 2 | 一条正常和一条受控失败路径完成 User → Agent → Tool → Business System → Result，并有同次运行轨迹 |
| 3 | 展示超时、有限重试、错误工具/参数、重复/幂等、注入/授权和高风险审批 |
| 4 | 版本化 50～100 条评估集、冻结留出集、指标分母、Baseline 与 V1 同条件运行、错误分类 |
| 5 | 只针对最大错误类别做一项可归因优化，复跑相同评估并检查回归、成本和延迟 |
| 6 | 新环境可复现、含失败恢复的完整 Demo、核心版本与证据账本完成 |
| 7 | 可选：更深对抗/故障测试、可移植性或复用同一核心的第二场景 |
| 8 | 可选：README、架构叙事、Demo 视频、面试复现演练与最终证据审计 |

**Rationale**: 纵向切片尽早检验最危险假设；安全、评估和观测逐步加入，而不是最后补票。

**Alternatives considered**:

- 后端、前端、Agent 分层横向完成：拒绝，数周内无法验证真实闭环。
- 第二个 Happy Path 优先于失败处理：拒绝，增加演示宽度但不增加工程可信度。

## Decision 9 — Must / Should / Nice 由求职证据贡献决定

**Decision**:

- **Must**: 一个目标用户与企业痛点；一个主工作流；Agent/确定性逻辑边界；工具契约与业务状态变化；成功/失败验收；Baseline/V1 评估；同次运行观测/审计；最小权限、参数验证、读写隔离、审批、幂等；可复现 quickstart；风险和简历证据账本。
- **Should**: 复用同一核心的第二场景、故障注入、一个针对性人工审批、契约一致的真实外部适配、由错误分析驱动的一次优化、适度可用性与重复评估自动化。
- **Nice / default cut**: 多角色、多 Agent、长期记忆、通用编排平台、无必要性的 RAG、多 SaaS 集成、完整 RBAC/后台 CRUD、微服务/事件基础设施、多供应商抽象、复杂仪表板、集群编排与炫技 UI。

任何 Must 至少直接支撑业务价值、真正 Agent 判断、可靠安全或实测结果之一，并且是第 2 周切片或第 6 周求职证据所必需。

**Rationale**: 差异化应来自真实问题、失败处理和实验，而不是组件数量。

**Alternatives considered**:

- 把常见 JD 关键词全部设为 Must：拒绝，违反 6～8 周约束且混淆不同岗位轨道。
- Nice 仅写“以后做”：拒绝；部分技术应明确不采用，减少面试时无法解释的空洞范围。

## Decision 10 — 评估和简历主张采用证据账本

**Decision**: 每个量化主张记录准确措辞、状态（目标/已测/批准）、版本、数据集标识和哈希、样本量与分母、模型/配置、工具权限、重试/Token/时间预算、指标公式、原始运行、复现方式和限制。只有 `approved` 主张可作为既成简历成果。

Baseline、V1、Optimized 必须在同一数据、工具权限和预算下比较；若环境变化则全部重跑或标为不可比。报告计数与比例（如 43/60），延迟至少报告中位数与 p95，并说明是否包含重试；随机输出在可行时重复运行。开发集可指导优化，冻结测试集只用于最终结论；任何排除项必须在查看头部结果前记录。

确定性判定优先于模型裁判；使用模型评分时固定裁判版本并抽查争议样本。此方法与 OpenAI 对上下文化 golden set、早期 50～100 输出错误分析、评估预算与有效性披露的公开建议一致。[Evals drive the next chapter of AI](https://openai.com/index/evals-drive-next-chapter-of-ai/)；[Trustworthy third-party evaluations](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)

**Alternatives considered**:

- 项目结束后回忆指标：拒绝，易丢失条件与失败样本。
- 只报告最好一次运行：拒绝，构成 cherry-picking。
- 用供应商名和组件数替代结果：拒绝，无法证明业务或工程能力。

## Decision 11 — 外部系统默认采用契约真实、声明诚实的替代路径

**Decision**: 若真实企业账号、数据或 API 不可获得，核心版本使用业务语义真实、契约可验证的本地/合成系统；真实外部适配器只能作为 Should。README 和简历必须准确写明模拟边界。

**Rationale**: 强制真实 SaaS 会把认证、限流、费用和数据许可变成项目单点风险；业务规则、工具风险和幂等仍可通过契约真实的系统得到可信验证。

**Alternatives considered**:

- 必须接入多个真实 SaaS：拒绝，依赖不可控且面试价值未必增加。
- 只做无状态 mock：拒绝，不能证明真实业务状态、事务和重复调用安全。

## Research Closure

Phase 0 的规划未知项已解决：

- 招聘样本范围、来源等级、纳入/排除与去重方法已确定。
- 能力信号的统计语境与置信度规则已确定。
- 候选门槛、评分锚点、不确定性和反证流程已确定。
- 6+2 周范围、周门槛、过度工程削减和简历证据规则已确定。
- 最终 Agent 项目及其技术栈仍有意保持未选择状态；它们必须由后续完整市场分析、候选比较和反证决定，而不是本计划中的未解决澄清项。
