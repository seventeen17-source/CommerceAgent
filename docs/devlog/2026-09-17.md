## 遇到的问题

- **uv 官方文档描述的是 ≥0.12 的行为，本机是 0.11.28，实测不一致**：文档称应用模板默认定义 build system 并把源码放进 `src/`，但 0.11.28 实测生成的是根级 `main.py` 且**没有** `[build-system]`。结论：涉及工具版本的结论必须用本机 `--help` 与临时目录实测确认，不能只读文档。
- **命令行退出码不能作为唯一判据**：`uv add --dev` 之后整条 PowerShell 命令返回 `exit code: 1`，但 `pyproject.toml`、`uv.lock`、`.venv` 与导入 smoke test 全部正常。以产物为准。
- **控制台输出编码会污染判断**：PowerShell 输出中的中文会乱码，用 `Select-String` 匹配中文标题会静默失败，一度让我误判 devlog「只有 32 行」。判定文件内容必须用专用读取工具或 `git diff`，不能只看控制台输出。
- **本会话沙箱把 uv / npm 的缓存与 Python 安装目录挡在工作区之外**：uv 默认写 `%LOCALAPPDATA%\uv\cache` 与 `%APPDATA%\uv\python`，npm 缓存与 `~/.npmrc` 也在工作区外，`workspace-write` 下均被拒绝。为了让生成的工程与用户真实环境完全一致（而不是把解释器塞进临时目录），相关命令使用了提权；最终 `.venv` 正确指向 `%APPDATA%\uv\python\cpython-3.13-windows-x86_64-none`。
- **`npm install` 首次以 `ECONNRESET` 失败，原样重试即成功**：失败信息为 `Invalid response body while trying to fetch https://registry.npmmirror.com/react-dom: read ECONNRESET`。事后用 Node 实测两个 registry（npmmirror / npmjs）均返回 200，重试亦成功，判定为**瞬时抖动而非配置错误**。启发式：**先确认可复现性，再动配置** —— 否则会为一个不存在的问题改动机器设置。
- **npm 原本没有配置代理**：`~/.npmrc` 只有 `registry=`，`proxy` / `https-proxy` 均为 `null`。按用户指示配置 `http://127.0.0.1:7892` 后 `npm ping` 稳定返回 `PONG 1326ms`。
- **Windows 默认执行策略会让 `npm` 直接不可用**：在 PowerShell 里敲 `npm run build` 报 `无法加载文件 E:\node\npm.ps1，因为在此系统上禁止运行脚本`。根因不是 npm 坏了，而是：Node 同时提供 `npm.ps1` / `npm.cmd` / `npm` 三个入口，PowerShell 优先命中 `npm.ps1`；而本机 `Get-ExecutionPolicy -List` 的所有作用域均为 `Undefined`，回落到 Windows 默认的 `Restricted`，禁止运行任何 `.ps1`。
  - 绕过方式：显式使用 **`npm.cmd`**（`npm.cmd run build`、`npx.cmd`），零配置改动。
  - 永久修复需改机器安全策略（`Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`），属安全策略变更，未经用户确认不做。
  - **对项目的意义**：默认 Windows 环境 clone 本仓库后，照 README 敲 `npm run build` **必然失败**。因此涉及前端的文档/脚本应写明 `npm.cmd`，否则会变成一个人人都会踩的可复现性坑。

## 关键决策

- **uv 使用默认 app 模板，不用 `--package`**：`plan.md` 期望的 Python 结构是 `agent-service/app/...`，而 `--package` 会生成 `src/agent_service/` 并引入 build system，与之冲突；本服务是应用而非要发布的库。模板样例 `main.py` 删除，FastAPI 入口留给 T018 的 `app/main.py`。
- **Python 侧数据库驱动 = psycopg 3**：依据是 `langgraph-checkpoint-postgres` 的官方依赖声明（`psycopg>=3.2.0` + `psycopg-pool>=3.2.0`），而非偏好；不引入 asyncpg（避免两套驱动），V1 也不引入 SQLAlchemy / Alembic（迁移权威在 Java 侧 Flyway）。原设计文档未指定该驱动，已补记为 `research.md` 决策 16。
- **`langgraph-checkpoint-postgres` 在 T003 就加入**：决策 9 要求 checkpoint 持久化，且它正是「驱动选 psycopg」的依据；若推迟到 T017 再加入，当前的 `psycopg` 依赖会失去依据。
- **前端工具链版本跟随 create-vite 官方模板**：模板钉的是 `typescript ~6.0.2`，而 `plan.md` 原写 `TypeScript 5.x`。选择保留官方组合（实装 6.0.3），不手工改写版本；`plan.md` 已同步修订，并补记为 `research.md` 决策 17。另注意模板的 lint 工具是 **oxlint**，不是 ESLint。
- **npm 代理只写用户级 `~/.npmrc`，绝不写进仓库**：把 `localhost` 代理提交进项目会让其他机器 clone 后无法安装依赖。备份在 `%TEMP%\npmrc.bak`。
- **不给 Maven / uv / 系统级代理环境变量加代理**：Maven（`repo.maven.apache.org`）与 uv（PyPI）**直连实测均成功**，加代理只会多一跳，且可能在代理重启时把本来可用的构建搞挂。代理审计结论：git ✅ / npm ✅（今日补） / Docker ✅（用户修复） / Maven 未配但直连可用 / uv 未配但直连可用 / 系统级变量保持为空。

## 今天学到

- **依赖的「声明」与「锁定」是两个文件，而且锁文件里还存着声明的副本**：`pyproject.toml` 写范围（`fastapi>=0.141.1`），`uv.lock` 写精确版本与哈希。`uv.lock` 内部第 27 行的 `specifier = ">=0.141.1"` 是**声明的指纹**，第 226 行的 `version = "0.141.1"` 才是**锁定的事实**；判断时必须看对 `[[package]]` 区块的归属。
- **`--locked` 挡的是「声明漂移」，不是「结果漂移」**：实测把 `>=0.141.1` 放宽为 `>=0.141.0` 后，`uv sync --locked` 仍然报错 —— 尽管解析结果一个包都没变（`Resolved 58 packages`）。因为变的不是结果，是声明。
- **npm 与 uv 的语义对照**：

  | uv | npm | 语义 |
  |---|---|---|
  | `uv add` / `uv lock` | `npm install` | 允许重解析，**会更新 lock** |
  | `uv sync --locked` | `npm ci` | lock 必须与声明一致，否则**报错** |

- **`.python-version` 与 `requires-python` 不是同一件事**：前者是本工程实际使用的解释器版本，后者是项目声明的兼容范围（包元数据）。
- **TypeScript 的类型在产物中完全不存在**（type erasure，类比 Java 泛型只在编译期存在）。证据在配置里而非口头：`web/tsconfig.app.json` 有 `"noEmit": true`，说明 `tsc -b` **不产出任何 JS**，`build` 里的 `tsc` 只是类型检查闸门，真正把 `.tsx` 变成 `.js` 的是 Vite；同文件的 `"erasableSyntaxOnly": true` 正是为「直接剥类型」服务的。
- **Vite 开发模式不是打包工具**：`vite dev` 用浏览器原生 ES modules 按需加载，只做 TS→JS 转换与依赖预构建；只有 `vite build` 才把 20 个模块合成 `dist/assets/index-*.js`。
- **前端产物概念的对应关系**：`node_modules` ↔ `.venv`（依赖，不入库）；`dist` ↔ `target`（构建产物，不入库）；`package-lock.json` ↔ `uv.lock`；`package.json` 的 `scripts` ↔ `pom.xml` 的插件配置。
- **`tsconfig.json` 是 solution 文件**（`files: []` + `references`），只负责串联 `tsconfig.app.json` 与 `tsconfig.node.json`，等价于 Maven 多模块的 aggregator pom。
